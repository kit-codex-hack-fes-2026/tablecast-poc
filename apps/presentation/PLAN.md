# TableCast 動画制作計画 — 初期計画の記録

## 現在の作業目的（2026-09-12・ユーザー再確認）

目的は[Issue #1「Openscreen + Hyperframes + TTS (Inworld, irodori, ...)でデモ動画作成基盤を実装」](https://github.com/kit-codex-hack-fes-2026/tablecast-poc/issues/1)の実装。以下の初期計画や個別動画の修正より、この目的と最新のユーザー指示を優先する。

- `apps/presentation`にOpenScreenの実収録・編集、HyperFramesの構成・演出、TTSのナレーションをつなぐ制作基盤を置く。生成コードと素材をリポジトリで管理し、録画・画像・音声等はGit LFSで扱う。
- 現在の2本の動画は基盤の出力例。UI・商品・仕様の更新後に再収録し、実際の応答に合わせて字幕・カット・注目箇所・説明を更新して再生成できることを軸にする。保存済み素材の再書き出しだけで変更へ追従できたとは扱わない。
- 現状は再収録と素材の再書き出しが分かれ、カット位置・字幕・素材参照には手動更新が残る。基盤の完成と個別MP4の書き出し完了を区別する。
- Issue本文の「以下は参考程度に」以降は参考案。ユーザーと合意した要件を優先し、汎用動画サービスや無関係なフレームワーク移行へ範囲を広げない。
- デザイン・アニメーションの改善も再利用する構成へ反映する。評価はユーザーが行い、レビュー発言だけで実装修正を開始しない。

## 初期計画の記録

以下は初期計画。2026-09-12の追加レビューにより、商品紹介は120秒固定から「2分程度・自然なテンポ優先」へ変更した。現在の台本・実装・成果物は[README.md](README.md)と[WORKFLOW.md](WORKFLOW.md)を参照する。画像の採否と見た目のレビューはユーザーが行う。

2026-09-12のレビューに基づく制作計画。2本の構成実装と試作を行った後、最新のユーザー指示により制作環境の確認を優先している。現在の検証状況は[WORKFLOW.md](WORKFLOW.md)を参照する。新たなClaudeレビューやComfyUIの導入・使用は行わない。見た目・演出の良し悪しはユーザーが評価する。

## 1. 目標と成果物

目的は、UI・商品・仕様の変更後も再収録・差し替え・再生成できる制作基盤。次の2本を独立して生成・再生・更新できるようにする。

| 成果物                     | 尺    | 視聴者に伝えること                                       | 出力予定                                    |
| -------------------------- | ----- | -------------------------------------------------------- | ------------------------------------------- |
| 商品紹介・実動デモ         | 120秒 | 誰が、どこで使い、相談から注文・店舗対応まで何ができるか | `output/tablecast-product-demo.mp4`         |
| 技術詳細・評価基準との対応 | 60秒  | なぜ動くか、設計の根拠と4つの評価基準への対応            | `output/tablecast-technical-evaluation.mp4` |

1920×1080、30fps、H.264/AAC、焼込み字幕＋独立VTT。映像フレーム数は3,600と1,800を目標にする。最後の音声と余韻が収まるよう台本を先に調整し、発話の途中を切って尺を合わせない。

単一の台本正本から2本を指定してビルドする。作業ディレクトリ・timing・字幕・MP4は動画ごとに分ける。旧 `output/tablecast-demo.mp4` を上書きしない。共通素材は参照し、台本を派生HTMLや別の短縮台本へ複製して編集しない。

図は一枚を過密に縮小せず、詳細アーキテクチャ、ERD＋状態遷移、開発証拠の3画面に分けて密度を上げる。音声ですべてのラベルは読まない。台本の発話IDを基準に丸囲み・経路強調・拡大を同期する。

### 評価基準への対応

[Issue #1](https://github.com/kit-codex-hack-fes-2026/tablecast-poc/issues/1)に記載された4項目・各25%を計画の前提とする。主催者の原文を別途確認できた場合は表記を照合する。

| 評価項目     | 説明する価値                                   | 動画に載せる根拠                                                                                    |
| ------------ | ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Codex活用    | 要求から実装・検査・修正・資料生成までの活用   | 実Issue、差分、テスト結果、レビューと改善履歴。コード量やツール数を成果の代用にしない               |
| インパクト   | 客の相談・注文と店員の対応がつながる           | 実アプリでの相談、確認・承認、同じ注文の店舗側表示。省力化・売上など未測定値は主張しない            |
| 展開性       | 店舗の商品情報・接客設定を変えて利用できる構造 | 設定と業務ルールの境界。時間内に第2の商品・設定への変更を実証し、難しければ構造の説明と未実証を区別 |
| デモとピッチ | 目的、操作、確認、結果まで一貫して追える       | 商品紹介編の一連の実演、端末・役割表示、音声停止時の継続、動画自体の完成度                          |

## 4. 共通の演出方針

- 端末フレームはHyperFramesで管理。客はiPad横1024×768、店員はiPhone縦390×844、管理者はMacBookの1440×900ウィンドウを収録基準とする。実機ではなくviewport再現であることを明示。端末内画面と外側16:9を混同しない。
- UI本文が小さい問題は、正しいviewportと操作対象へのズームで解消する。既存1600×900の映像をiPadの形に引き伸ばさない。操作前の全体表示→対象を指す→操作→結果→全体へ戻す順で編集。
- OpenScreenは実録のカーソル、操作ズーム、cutを所有。HyperFramesは端末枠、字幕、章題、技術図、場面転換、BGM/SEを所有。OpenScreen済み素材へ同じズームを重ねない。
- 字幕は話者名を必須にし、話者色は試案として付ける。ナレーション、客、キャスト、操作説明を区別。要約や生成音声入力の表示も維持する。
- 導入には同じ人物・店・端末でつながる生成画像2〜3場面と、短い生成動画を想定。既存画像は参考素材として利用。生成動画の実行先・利用可能性・費用は制作開始時に確定する。画像のパン/ズームを生成動画と呼ばない。
- Motion Graphicは、導入のテンポ、端末の登場、画面間の接続、確認から確定への変化、技術経路の流れに使う。文字が読める時間を取り、発話に対応する動きと装飾を区別する。演出の強さはユーザーの見た目レビューで調整。
- 音は歌なしBGMと少数のSE（章転換、注目、確認完了）。実会話・ナレーション中はBGMを下げる。アプリにない音をアプリの実音として説明しない。
- デザインシステムの本格共通化は[Issue #89](https://github.com/kit-codex-hack-fes-2026/tablecast-poc/issues/89)の確定後に反映する。現時点の方針（白黒、Noto Sans CJK JP＋Inter、Agentだけに虹色、意味のある分類色）を尊重し、字幕・脚注の帯は分ける。暫定スタイルは既存styles.cssへ集約し、共有packageを新設しない。

## 5. BGM/SEの調達とArtlist

候補曲1〜2本とSE3〜5個を先に選び、購入判断を具体的にする。現時点で契約は行わない。試作は利用条件を確認できる音源または既存の利用可能な音源で進め、正式音源へ差し替えられる参照にする。

2026-09-12確認時、[Artlist公式ヘルプ](https://help.artlist.io/hc/en-us/articles/29559573229725-Artlist-s-Music-and-SFX-plans-explained)ではMusic & SFX Proは年払い、Socialは月払いまたは年払いで対象用途が異なる。「月1,500円で1か月だけ契約すれば今回の全用途を満たす」とは未確認。会場上映、公開先、チーム利用、将来の再編集の条件まで比較してから決める。

有料ライブラリの原音は、そのまま公開Git/LFSへ入れない。[公式ライセンス](https://artlist.io/help-center/privacy-terms/artlist-license)に従い、曲名・作者・取得元・ライセンス・取得日・対象動画と再取得手順を記録する。公開して再配布できる素材とローカルのみの素材を区別する。

## 6. 制作工程

1. **台本と証拠を確定**: 120秒/60秒の文章、発話、実操作、図の主張、4基準の根拠を対応付ける。既存素材の採否と再収録箇所を整理。Claude Code CLIで設計レビュー。
2. **収録・OpenScreen経路を完成**: 正しい3viewportで実操作を収録。OpenScreenのカーソルとズーム、project保存、MP4 export、可搬化を通す。現在の25秒は静止画面のパイプライン試験なので、新たな操作実演が必要。
3. **台本から2本を生成できるよう実装**: 端末、話者、素材、技術図・強調、BGM/SEを必要最小限追加。出力先を分離。TTSは発話変更分だけ明示生成し、通常テストに含めない。Claude Code CLIで差分レビュー。
4. **代表区間で統合確認**: 商品編は生成導入→iPad実操作→字幕・音、技術編は詳細図→発話に同期した強調を先に書き出す。ユーザーの見た目評価を反映する。短い確認用も同じ台本から抽出する。
5. **120秒と60秒を独立レンダリング**: 音声の末尾、各cut、役割表示、素材の比率、欠落・文字切れ、復号、同期、音量、再生を技術的に確認。2本とも単体で意味が通る構成にする。
6. **再利用を実証**: 商品紹介の録画を1本、技術図または表示文を1か所交換して再生成。不要なTTS再課金、もう一方の出力上書き、台本の二重編集がないことを確認。手順・素材出典・検証結果を残す。

## 7. 役割と完成判定

ユーザー: 見た目、演出の気持ちよさ、テンポ、伝わりやすさ、曲や声の好みを評価する。

Codex: 台本と実装の整合、収録の実体、端末比率、文字の欠け・重なり、字幕と音声の配置、clip範囲、無課金テスト、動画の尺・復号・再生、素材交換と再生成を検証する。Claude Code CLIによる節目のレビューと指摘修正を行う。

既存diff・元録画・課金済み音声・旧完成動画は保全する。commit、push、PR、Issue変更は行わない。実機・実店舗の雑音・負荷試験を動画の成功から推定しない。既知の音声上限や再開時の状態上書きはアプリ側の未解決事項として区別する。
