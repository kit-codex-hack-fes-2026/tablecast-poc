# 動画生成基盤の再利用性監査

2026-09-13。対象：Issue #1、`apps/presentation` の現行作業ツリー。アプリ側HEADは `17dc3328960e653006854b6edc8d829e4063f80e`。presentation自体は未追跡のため、このSHAだけでは生成基盤の版を復元できない。

ユーザー指示により動画の仕上げは一旦区切る。商品紹介v13／技術紹介v16を維持し、今回の作業は監査と隔離した検証に限定した。実装変更、新規の実アプリ撮影、有料TTS、完成MP4の再出力は行っていない。

## 判定

**保存済み素材を編集・合成する基盤は成立している。一方、アプリが変わっても同等の品質を再現する制作基盤としては、まだ実証が足りない。**

これは「完全自動化していないから不合格」という判定ではない。題材ごとの構成、台本、撮影手順、図の意味を人またはCodexが判断することは自然である。問題は、その判断を支える再利用可能な入力・検査と、今回の題材・テイクに固有の処理の境界が十分に分かれておらず、第二の題材で工程全体を通した証拠がないことである。

| 変更の範囲                    | 現時点の判定         | 根拠・制約                                                                                |
| ----------------------------- | -------------------- | ----------------------------------------------------------------------------------------- |
| 同じ保存素材からの合成        | 検証済みの土台がある | 2本を隔離buildし、HTML・字幕・timingが現行distと一致。今回MP4は再renderしていない         |
| 台本・図の文章や構成変更      | 部分的に再利用可能   | 別名の2場面を生成できる。ブランド表記はコードに残る。図の配置と発話の対応は編集判断が必要 |
| TableCastのUI・動作変更に追従 | 未完了               | 撮影対象の実測はあるが、現行実録の大部分は新方式の証跡検査対象外                          |
| 別アプリへの移植              | 工程全体は未実証     | 撮影URL・業務状態・操作順・品質検査がTableCastに依存                                      |
| 別PC・新規checkoutからの復元  | 未実証               | LFS設定はあるがpresentationは未追跡。OpenScreenの場所・Windows録画寸法にも前提がある      |

## 再利用できる部分

- `tablecast-project.ts`：Zod入力検証、シーン抽出、実音声尺に基づくtimeline、素材範囲外・字幕衝突・不正な強調時刻の拒否。
- `tablecast-tts.ts`：有料APIの入口分離、発話と音声設定によるWAVキャッシュ、保存音声の検証。見出しや配置だけの変更で再課金しない。
- `tablecast-shot.ts`：対象の可視性、文字、矩形の安定、保持時間の実測と定義ハッシュ。`tablecast-zoom.ts`／`tablecast-cursor.ts`：対象に合わせた拡大と実操作ポインターの合成。
- HyperFrames＋GSAP＋CSSによる合成、OpenScreen projectによる編集、FFmpegによる前後処理。これらを別製品に置き換える必要は現時点ではない。
- GENERATION／WORKFLOW／CAPTUREに、機械検査と内容・見た目の採否を分けた手順がある。

## 優先して解消すべき差

優先度は「別アプリでも同品質を再現する」という今回の目標に対するもの。現在の動画に同じ優先度の不具合があるという意味ではない。

### P1：撮影定義を差し替えても、撮影先と業務フローは差し替わらない

根拠：`scripts/tablecast-project.ts:333` は別台本の指定時も固定の `capture-plan.json` を読む。`scripts/tablecast-shot.ts:12,170` は注文関連の4状態と `/api/table` の応答構造を所有する。`scripts/tablecast-record-guest.ts:19,175,221` はmainのURLと相談→注文→読了→承認を固定し、`scripts/tablecast-record-role.ts:70` は店舗IDと管理画面のルートを固定する。

別アプリの台本を入力する隔離試験では、schemaとbuildは通過したが、`readCaptureProject()` は `撮影対象の場面がありません: consult-answer` で停止した。予約作成やチケット更新の撮影へ、そのまま切り替えることはできない。

最小の対応は、実際に選ぶ第二アプリの撮影手順と状態確認を題材側へ置き、共通処理には対象の実測・録画・編集を残すこと。URLや入力ファイルの指定も同じ題材を参照させる。汎用の操作DSLやプラグイン基盤を先に作る必要はない。移行時はTableCastの状態待ちを維持し、未成立の結果を撮影成功にしない検査が必要。

### P1：新しい撮影・証跡方式が完成動画の全工程では実証されていない

根拠：現行 `sample.json` のmedia付き12場面中、`capture` と `media.shot` の両方があるのは `admin` の1場面。客10場面と店員1場面にはない。`scripts/tablecast-build.ts:93` の撮影証跡検査は `scene.capture && scene.media` の場合だけ適用される。旧素材が誤っているという意味ではなく、build通過から新撮影方式の全面適用を推論できない。

CAPTURE.mdの実行記録にも、新しい客側撮影は注文成立まで未完成と記載されている。また、撮影定義のハッシュは検査しても、同一定義のまま変わったアプリ実装との鮮度は自動判定しない。技術の `sources` もbuildではファイルの存在確認にとどまる（`tablecast-build.ts:47`）。

最小の対応は、新方式で開始状態→操作→結果まで一つの実デモを収録し、音声・字幕・ズーム・完成動画まで通すこと。その成功を残してから必要な場面へ適用を広げる。実装の版と撮影日時を証跡へ関連付け、古い素材を使う場合は適用範囲を明示する。旧完成品へ一律に証跡を必須化すると再生成を壊すため、既存素材と新規素材を区別した移行が必要。

### P2：見た目の再利用と題材の分離が途中

根拠：`scripts/tablecast-build.ts:175,253,361,386` にTableCastの画面枠・末尾・ヘッダー・HTMLタイトルが直接記述されている。別名「BookFlow」の台本をbuildした実DOMにも、ヘッダー2か所のTableCastと旧HTMLタイトルが残った。

技術図には編集可能なパネル・線・強調の共通表現がある。一方、`tablecast-technical-schema.ts` は座標指定であり、内容から適切な図式や読み順を決める仕組みではない。今回の04〜06のような構成判断は、図式の選択と配置・発話調整の制作工程に残る。

最小の対応はブランド・話者表示の題材別入力と、既存の図式ごとの作例・選定条件を用意すること。例：主体と接続は構成図、処理順はシーケンス、成立条件は状態遷移、実測比較は軸・単位・条件を持つグラフ。1920×1080、日本語、固定フォントを同品質の標準プリセットにすること自体は問題ではない。第二アプリで不要と分かった制約まで先回りして可変化しない。

### P1：品質検査の入口が現在の作品に固定されている

根拠：`scripts/tablecast-layout.spec.ts:1,9,36` は `sample.json`、`dist/product|technical`、`roles|tech-intro` を直接参照する。ほかにも既存の場面名・役割に対する検査がある。`TABLECAST_PRESENTATION_PROJECT` やbuildの `--out` を変えても、通常の配置テストはその別出力を検査しない。

最終MP4の復号・音量・再生等はWORKFLOW.mdにあるが、v16で使った実行スクリプトはignore対象の `output/tablecast-verify-v16.mjs`。対象版と比較ハッシュが固定で、56行目の単体40件・ブラウザー6件等は実行結果を読み取らず記入する形式。今回の実際の検査成功を否定するものではないが、次の作品へコピーすると古い成績を残す余地がある。

最小の対応は、既存検査へ入力台本・対象出力・完成MP4を渡せる入口を持たせ、全作品共通の検査とTableCastの内容検査を分けること。成績は実行結果から記録し、未実施は未実施とする。現在の検査を削らず、新しい場面名でも実際の対象が検査されたこと、故意の文字切れ等を不合格にできることを確認する。

### P2：制作環境と検証記録の引き渡しが未完了

根拠：監査時 `git status --short` で `?? apps/presentation/`。`.gitattributes` に素材のLFS設定はあるが、設定の存在はcommit・LFS upload・別checkoutの取得成功を意味しない。`output/` はignore対象で、`claims.json` の一部の根拠もその中の実行記録を参照する。`scripts/tablecast-edit-guest.ts:56` は元録画1026×850を要求し、その下のcrop値も実測済みWindows配置に固定されている。

最小の対応は、正本・採用素材・必要な証跡・ツール条件を実際に保存し、新規checkoutまたは別作業環境で取得から確認まで通すこと。全ての過去テイクや巨大な検査画像をGitへ入れる必要はない。参照される証跡の保存先を一貫させる。commit・push・新環境検証は今回実施していない。

## 同等の品質を作れる、と判定するための次の実証

次は大規模な一般化より、**実在する第二アプリで短い1本を工程全体に通し、そのアプリを一度変更して再生成する試験**を行うのが適切である。第二アプリは今回の監査用架空台本では代用できない。

1. 利用者の目的、開始状態、操作、成功結果を定義する。既存の台本・撮影・編集方式で作り、共通コードを変えた箇所と題材側だけを変えた箇所を記録する。
2. 新規録画、実応答に合う字幕、ナレーション、対象実測、ズーム、適切な技術図、完成MP4まで通す。APIが有料なら、実証の実行範囲と費用をその時点で扱う。
3. UI位置・文言または一つの操作を変更して再実行する。旧対象を検出して失敗するか、新しい対象を実測して撮れること。固定座標や旧テイクの発話時刻の修正を共通コードに足して成功させない。
4. 台本のナレーションだけを変更し、変更した発話だけ再生成され、尺・字幕・強調の対応が検査されることを確認する。人が時刻を調整した場合も記録する。
5. 完成MP4を同じ観点で審査する：無音で目的と操作結果が追える、停止時に図の主体・関係・条件が読める、等速で発話と注目先が一致する、文字切れ・音切れがない、主張が実装と収録証拠に一致する。
6. 引き継いだ担当者または新規作業環境でも、必要な素材・設定・記録から同じ工程を実行できることを確認する。

所要時間、再撮影回数、手動調整箇所、共通コードの修正内容も残す。「生成できた」だけでは、毎回今回と同量の個別作り込みが必要か判断できないためである。機械検査合格と説明・見た目の品質判定を両方満たした時点で、再利用可能な制作基盤としての完成を評価する。
