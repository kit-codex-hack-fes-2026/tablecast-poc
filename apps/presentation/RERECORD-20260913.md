## 撮影で修正したこと

- 最新SSRの初期表示だけで撮影を始めると、hydration時にウィンドウタイトルが上書きされた。客側はメニューの操作が有効になるまで待ち、客・店員の撮影専用ウィンドウは録画対象を特定するタイトルを維持する。
- 接続表示が出てもAgent初期化が終わっていない場合がある。初回・再開時に応答用音声トラックの購読まで待つ。
- 過去の応答数だけで完了を判定すると、直前の応答終了を次の発話への回答と誤認した。入力後の`voice.user`のturn IDに対応する、実再生済み`voice.assistant`イベントを待つ。英語部分を別テイクで再収録した。
- 失敗時にも画面・音声・イベントを保存する。最初のguest-v1は認証準備前、v2は環境・初期化の問題、v3はタイトル消失、v4はSDK用資格の受け渡し不足で失敗。staff-v1もタイトル消失で失敗。これらは不採用のまま保持した。

## 起動環境

旧コンテナには最新mainの`tablecast-lgtm`サービスが不足しており、OTLP送信のDNS警告とAPIの応答待ちが発生した。当該Compose projectのLGTMだけを構成どおり起動し、API応答が回復したことを確認した。既存コンテナ全体の再作成やDocker全体の再起動は行っていない。

通常の音声起動は[セットアップ](../../docs/setup.md)に従う。今回の旧環境は`.env.secrets.local`を保持していたため、WebはそのファイルをBunで明示ロードして起動した。Pythonはuvへ直接渡した。SDK標準名の非秘密の対応式`OPENAI_API_KEY=${TABLECAST_MODEL_API_KEY}`だけを`/tmp/tablecast-rerecord-sdk.env`に置き、以下の順序でロードした。逆順では対応式が空になったため、値を出さず、有無と一致だけを検査して確認した。

```sh
# コンテナ内 /workspaces/tablecast。旧環境の今回の再現用。
bun --env-file=.env.secrets.local run dev:container
uv run --project livekit --env-file /tmp/tablecast-rerecord-sdk.env --env-file .env.secrets.local --env-file .local/.env.voice tablecast-voice dev
```

撮影後は今回起動したAgent、devと子プロセス、LGTMコンテナを停止した。既存の開発コンテナは元のidle状態、volumeと保全用stashは維持した。秘密値・認証状態はGit管理外に置き、共有する素材には含めない。
