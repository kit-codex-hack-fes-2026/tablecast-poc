## 客の分け方

一般客は、料理や地酒を発見したい客、自分の好みに組み立てたい客、初めての料理を皆で取り分けたい客に分ける。操作への慣れ、希望する言語、本人が申告した食事条件を重ね、年齢・国籍・名前・声から能力や信条を推定しない。一卓の複数人で同じカート・確認・会計を共有する。

## 一卓に複数人が話す場面

交互に話す、客同士の声が重なる、本物の店員の説明中に割り込む、確認中に訂正する場面を用意する。話者の識別ができなくても、商品・構成・数量が明確なら同じカートで扱う。曖昧なら聞き直し、本人・席・人数・個別会計を話者番号から作らない。

`burger-04`と`burger-05`は250ms差で客同士の声を重ね、その後の`burger-06`で内容を明確に言い直す。聞き返しは許容し、重なった全単語を完璧に聞き取ったことを成功条件にしない。韓国料理では`korean-05`と`korean-06`を300ms差で重ね、`korean-07`でセット数・チヂミ数量・ボトル数と器の人数を言い直す。`burger-07`、`dietary-04`、`confirm-03`、`korean-08`は実際の店員TTS開始を観測してから挿入する。固定音声ファイルの中へ想定の店員返答を混ぜない。

### 台本と保存済みfixture

[dialogue.json](dialogue.json)は8シナリオ・52の客発話と、別枠3のAI店員参考例を持つ。これは音声素材生成と将来の実有料E2Eに使う入力資料であり、E2Eの実行・合格を表さない。

既存の[会話fixture](../../scripts/tablecast-seed-data.ts)は、各店T02に2人が数量を2個から1個へ訂正する合成会話と、speaker IDがnullの発話を保存する。`source: synthetic-demo`、historyは`synthetic-history`として区別する。この保存ログを52発話の実認識結果へ置き換えたり、台本の名前を認識結果へ注入したりしない。現在のRealtime字幕には話者IDがないため、実演の字幕はお客さまの表示を使う。

## 従業員と管理者

各組織にowner・admin・memberを1名ずつ置く。こもれびとハヌルのownerは同じ佐藤晴香であり、人物は8名・所属は合計9件となる。[共通名簿](../../apps/emulate/src/tablecast-demo-identities.ts)をseedとGoogle OAuth模擬ログインで共有する。客の音声ペルソナと組織のメンバーを同一人物として扱わない。

| 役割               | 目的                       | デモで行うこと                                                                 |
| ------------------ | -------------------------- | ------------------------------------------------------------------------------ |
| member・ホール担当 | 必要な対応を把握する       | 提供待ち・呼出し・会計待ちを確認し、受付・提供・呼出解除・支払登録・閉卓を行う |
| admin・店長        | 営業とメニュー変更を整える | 下書きの翻訳・売切を確認し、会話注文デモと差分確認から公開する                 |
| owner・店舗責任者  | 店固有の接客と導入を整える | 店舗資料からMCPで設定下書きを作り、対象版を確認して公開する                    |

[店舗側Agent Plugin台本](staff-plugin.md)では、佐藤晴香の資料からの初期設定、田中蓮の注文傾向からの施策、小林直子の食べ方案内、中村美咲の売切対応、山本翼の季節商品準備を具体的な依頼と応答にする。各店の接客・お品書きの提案も含める。

将来の分析では商品・会計等の基本集計を店舗が利用する外部分析環境へ渡す。英語設定の来店を外国人観光客の属性と同一視せず、取得した情報の定義を示して施策の仮説に使う。顧客の年齢・性別・宗教を音声から推定して集計・評価するシナリオは作らない。
