## Mobbinから採用する構成

[Grainの利用場面](https://mobbin.com/sites/sections/71142411-6989-45b4-8666-0aa2482723fd)は、用途ごとに実画面・短い見出し・成果を隣接させている。[Loomの用途案内](https://mobbin.com/sites/sections/455f1979-870a-4984-a41b-d1605ae65a42)は、役割を短い名前で選べる。どちらも飲食業向けではないため、構成の参考として用いる。

TableCastでは写真だけで利用価値を説明せず、対応する実画面を隣に置く。長い5場面を読み進める前に、料理選び・多言語接客・声で注文・導入準備・スタッフ対応の入口から対象場面へ移動できるようにする。配色・書体・ボタンはTableCastのデザインシステムを維持する。

## スライドの使い方

[pitch.md](pitch.md)は、作品の価値（こだわり・愛情、独自性、可能性）と完成度（機能、内容、デザイン・UI・UX）を伝える原稿。元の説明・表・画像・会話全文を保持する。構成図と検証の詳細は[技術説明用の別スライド](technical.md)へ移し、情報自体は残す。水平線ごとに1ページとし、HTMLコメントは登壇者の話す内容・操作・採用優先度を記す。

3分発表のうち、価値と完成度に約2分を使うことは選択肢として共有されている。これは原稿全体や画像を削る指示ではない。5枚構成や各ページの秒数は固定しない。実際に見せる会話デモの採用箇所を選び、原稿にある情報は読み合わせ・収録・補足にも使える形で保持する。

店舗側の導入のしやすさと、客側が料理を知って選ぶ楽しさを二つの柱にする。冒頭からAgent Pluginによる資料からの初期設定を示し、会話場面でその接客体験を見せる。注文・引き継ぎの後は、同じPluginによる営業後の振り返りと改善へつなぐ。店舗運営・会員機能・UIの工夫も原稿に残す。

店舗導入では、接続して対象店舗を確認する→お品書き・写真・店舗資料を渡す→価格や差分を確認して公開する、という店長の行動を示す。Agent Pluginの役割は資料の整理・下書き・確認事項の提示とし、公開は店が判断する。導入後の統計相談・改善提案も同じPluginから行い、採用案を下書き・確認・公開へつなぐ。客向けの音声会話を詳しくする変更で、この店舗側の価値を後景化しない。

## 会話で優先する価値

質問は、客が答えや専門用語を知らない状態から始める。最初の返答を聞いたからこそ生まれる追加質問を続け、料理を試したい、食べ方を比べたい、個別の確認をしたいという次の行動へつなぐ。商品名・写真・価格をそのまま読み上げる確認は、注文を成立させる段階に絞る。

| 場面             | 最初は分からないこと                           | 会話によって変わる選択                                     |
| ---------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 日本人4人        | 京都で何を食べれば地域らしさを感じられるのか   | 出汁巻きと地域のだし文化を知り、普段の卵焼きと比べて味わう |
| 日本酒を飲む二人 | なぜ温めるのか、ぬる燗とは何か                 | 同じ雪灯を冷酒とぬる燗で比べ、自分の好みを探す             |
| 旅行客3人        | 小皿からどう食事を組み立てるのか、だしとは何か | 食べながら選び、見えない材料への疑問も確認する             |
| 年配の夫婦・補足 | 思い出の料理名が分からない                     | 覚えている食べ心地を話し、近い候補を試す                   |

一般的なメニューにも文化説明は掲載できる。TableCastでは固定の説明だけで終わらず、その人の理解・好み・経験に応じて聞き返し、追加質問に答え、同じ会話から注文やスタッフ確認へ進める点を示す。文化の豆知識を一方的に長く読む場面にしない。

台詞はお客さまとTableCastの往復とし、英語には日本語訳を添える。客同士の掛け合いは置かず、タッチ操作や店員の動きは演出として分ける。全文を一枚へ投影する場合は文字が過密になるため、登壇用には同じ台詞を順に表示し、Markdownは読み合わせ用の全文として使う。

文化説明は農林水産省・日本政府観光局・日本酒造組合中央会の資料と照合する。地域の一般的な習慣と、この店の原材料・製法・提供条件を区別する。試し方は提案であり、味の感じ方や思い出の料理との一致を保証しない。追加した文化解説を現行店舗Skillへ登録し、実モデルで再現できるか確認する作業は収録前に残る。

素材の出所は[LP素材一覧](../../apps/web/public/landing/README.md)と[会話台本の素材・商品情報・文化説明の根拠](../../apps/presentation/assets/images/pitch/README.md)に従う。写真は利用シーンの表現、画面は実アプリの隔離fixture。台本の会話や注文合計を今回の実モデル・実操作で検証した画像とは扱わない。公開一覧の他作品画像を自作スライドの素材へ転用しない。実行結果は固定の件数をスライドへ焼き込まず、PRの最新SHAから確認する。

## 本番で実演する会話の優先度

| 優先度   | 場面                                             | 採用する理由と扱い                                                                             |
| -------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 主軸     | 日本人グループの文化相談→注文完了                | 知らない背景を聞き、試したくなった料理を選び、画面で確認して注文する。元の質問と応答を保つ     |
| 重要     | 旅行客の見えない材料の相談→スタッフへの引き継ぎ  | 料理の説明だけでは解決できない個別の確認を、人につなぐ。原文・要約・未注文状態が届く画面を示す |
| 候補資料 | 日本酒の温度比較、年配夫婦の思い出からの料理探し | 会話によって選択肢が広がる別の例。台本・画像は残し、本番で同じ役割のデモを重ねない             |

外国語の意味訳・転写・外貨参考表示はUIの工夫として残す。外国語会話の全文を削ったり、原稿から画像を外したりして尺を作らない。

## 収録と編集の方針

最初の一連の操作は実際の応答待ちも含め、等速・時間の省略なしで見せる。会話から注文完了、スタッフに用件が届くところまでが伝わる採用テイクを用意する。現状の台本では日本人の注文と旅行客の引き継ぎは別来店なので、続けて紹介するときは場面が変わったことを明示する。

以降の利用ケースや店舗導入は、必要箇所の抜粋・早回しを使える。編集のある映像だと分かる表示を付け、実際の応答速度や導入所要時間と混同させない。本番で採用しない会話・機能説明・画像も原稿には保持する。尺の調整は収録と編集の選択で行う。

本番は収録済み動画を使う案を基本にする。可能なら11インチiPadの実際の表示領域を記録し、客画面の文字・料理写真・注文確認が読める大きさで収録する。合成音声を外国語入力に使う場合は、入力素材と実モデルの応答を区別する。新規収録と動画全体の所要時間の確認は未実施。

元の共有会話にあった1組・4人だけの分析や、コカ・コーラ100円を追加した時点の状態は、今回の実行結果として使わない。新しい会話では、再取得した公開版4の61商品を基準に、英語説明1項目だけを変えた下書きを確認した。初期導入のお品書き・写真からの設定例は、引き続き想定利用例として保持する。
