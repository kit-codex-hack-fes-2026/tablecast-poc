# Seedとデモ用シナリオ

[索引](README.md) / [店舗・ペルソナ・収録資料](demo/README.md)

## 目的と同梱状態

そばで相談に乗る店員と、店固有のデザインを持つ紙のお品書きの体験を、音声と画面で高める。営業中の店舗を再現し、日英UI、カスタマイズ、一卓に同席する複数人、複数卓、会計、会話の録画に使えるようにする。
構成データは [tablecast-fixtures.ts](../scripts/tablecast-fixtures.ts) に実装する。生成画像は管理済みのローカル資産からR2へ投入する。DB投入結果と音声の実測結果は、構成データの件数とは分けて記録する。

[ペルソナ](demo/personas.md)、[店舗・内装・制服・お品書き](demo/stores.md)、[収録シナリオ](demo/scenarios.md)、[現行実装と将来機能](demo/capabilities.md)を分けて管理する。企画の画像や台本は実装・音声認識の証拠ではない。人物アバターの希望は独立Issueへ記録し、今回のseed変更には実装を含めない。

## プロファイル

| profile | 用途              | 目安                                                                       |
| ------- | ----------------- | -------------------------------------------------------------------------- |
| smoke   | 初回開発、最小E2E | 3組織・3店舗・6卓、各店4商品の合計12商品                                   |
| demo    | 動画、機能確認    | 3組織・3店舗・36卓、各組織3所属。京料理60・バーガー12・韓国料理30の102商品 |
| history | 大量履歴の確認    | 過去600セッション程度、注文2,000件以上、event20,000件以上                  |

`tablecast-komorebi`の京料理こもれび四条店、`tablecast-koharu`のWestward Burgers Kyoto、`tablecast-hanul`の韓国食堂ハヌル三条店を使う。こもれびとWestwardは既存IDを維持し、ハヌルは専用IDを持つ新しいデモ店舗として旧あかりに代わる。新規DB・明示リセットの初期構成は各店に専用組織とowner/admin/memberを1名ずつ用意する。通常の再seedで既存店舗や履歴を削除しない。こもれびとハヌルのownerは共通のため、8人・9所属となる。同じschemaの設定だけで表し、店舗固有if文で製品の見た目や業務ルールを切り替えない。
こもれびは架空日本酒28銘柄、和食24品、その他飲料8品の60商品を持つ。Westwardはバーガー・サイド・クラフトビール・ノンアルコール飲料の12商品、[ハヌル](demo/korean.md)は料理20品・アルコール5品・ノンアルコール5品の30商品を持つ。少量・大盛り・シェア用や追加具材は、別商品として増やすのではなく適切なカスタマイズで扱う。単品注文はプランを選ばない状態で提供する。
和食は温度・容量・味付け・薬味・数量付きトッピング、バーガーはバンズ・パティ・チーズ・ソース・具材抜き・追加具材、韓国料理は包み野菜・たれ・辛さ・追加具材・取り分ける器など、料理に適した必須・任意・数量選択を用意する。発泡清酒へ熱燗を指定したり、料理へミルクを付けたりしない。
プランは飲み放題、食べ放題、セットを少数の実ルールで表現し、ラストオーダー・上限・対象外オプションを試せるようにする。

[共通メンバー名簿](../apps/emulate/src/tablecast-demo-identities.ts)をseedとGoogle OAuthの模擬ログインで共有し、氏名・所属・役割・アイコンを一致させる。各組織3所属は新規DB・明示リセットの初期状態であり、通常の再seedで既存メンバーや編集した氏名・パスワード・手動メールを上書きしない。未所属のアカウント連携確認用ユーザーである小川凛は店舗メンバーに含めない。既知の旧デモメールは、IDと所属を保って人名@店舗名.comへ移行する。 [店舗ロゴとプロフィール写真](demo/identities.md)は生成WebPを共有する。空欄または旧seedのSVG URLだけを通常のseed・PR再配備で更新し、手動設定した画像は保持する。

## カタログと画像

架空の店舗・顧客を使い、実際の個人情報・会話を投入しない。価格帯、数量、販売状況は不自然な乱数にしない。
商品名、説明、speechName、aliasをja/enで保持する。架空日本酒は香り・味わいの設定と読み仮名を持ち、実在の蔵元や商品の評価と混同しない。英語の長い名称、難読の日本語も含める。
アレルゲンは確認済み・含有・交差接触不明・情報不足を区別し、合成データであることを文書化する。
画像は利用権が確認できるものをリポジトリまたは管理済み資産として用意し、出所と権利を記録する。起動するたび外部から無作為取得しない。
[商品102点の個別写真](demo/photos.md)を各店の料理と器に合わせて用意し、店舗間で同じ汎用画像を使い回さない。生成画像は実物写真と扱わず、`imageKind`は`illustration`とする。料理・材料の輪郭を切らず、対象の長辺85〜92%・四辺4〜7%程度の最小余白を目安にする。皿の縁だけは切れてよいが、器が比較対象なら全形を残す。客画面は正方形の枠で全体を収める`contain`表示にし、ホバー拡大で切り取らない。画像なし・読込失敗でも名称・価格と操作を保つ。
画像キーは[画像投入処理](../scripts/tablecast-seed-media.ts)がファイル内容のSHA-256と実際のPNG/WebP拡張子から作る`tablecast/images/<sha256>.<png|webp>`を使う。R2のcontent typeも実形式に合わせる。旧設定の`tablecast/demo/<name>.png`は互換配信専用で、新しい写真の正本にしない。
選択肢写真の設定・公開・客画面は[Issue #122](https://github.com/kit-codex-hack-fes-2026/tablecast-poc/issues/122)の上段PRで扱う。全92選択肢のうち63件へ62枚の写真を紐付け、辛さ・温度・なし等の29件は文言や記号で伝える。商品写真と、こもれび・Westwardの紙メニュー・内装・制服の雰囲気画像を分けて管理する。雰囲気画像は店舗テーマや人物アバターが実装済みであることを示さない。
アレルゲンの `verified` は合成レシピの登録確認を表す。実店舗の原材料確認ではない。含有を登録した商品と情報不足の商品を混在させ、交差接触とヴィーガン適合は未知とする。出汁・たれ・トッピングによる含有の変化も注意書きで伝え、安全を断定しない。

## 稼働中の状態

デモ店舗は空席だけでなく、接客中、カート編集中、注文確認中、提供待ち、スタッフ呼出、会計待ち、音声停止、音声障害を含める。
日英の客と、異なるUI言語を選んだスタッフの画面を同時に示す。
一卓の来店セッションに2〜3人が同席し、同じカート・確認・会計を共有する模擬会話を含める。台本の人物、登録した人数、音声が返す一時的な話者IDを区別する。現在のRealtime字幕には話者IDがないため、実演に架空の話者番号を補わない。複数人の交代・重なり・割り込み、未知speakerの扱いは[ペルソナ](demo/personas.md#一卓に複数人が話す場面)に記載する。
カート・送信済み注文・提供状態・支払済み・未会計の数字が整合するよう、同じ業務計算を使う。履歴の状態とevent順序を矛盾させない。

## 再現性

seed値、基準時刻、決定的なID生成を固定する。集合やhashの不定順序に依存しない。
固定の歴史データと、録画開始時点に相対配置する現在セッションを分離する。アプリ全体の時刻を偽装せず、デモ生成の起点だけを指定する。
毎回同じprofileから同じ初期状態へ戻せるようにする。重複seedで二重注文や残額の増加を起こさない。
D1の件数だけでなく外部キー、テナント境界、合計、プラン適用、状態、event順序を検証する。認証ユーザーはBetter Authの対応経路で作り、パスワードhashを手作りしない。

## 動画の進行

焦点となる一卓は人間の実操作専用にする。背景卓だけを台本で進め、録画中のカートへ勝手に別の商品を入れない。
背景進行も実際の業務API・状態遷移を通す。画面の数字だけを変更して動作を偽らない。
録画の代表経路は、日本語で日本酒と料理の相談→冷酒からぬる燗・容量等の変更→英語へ切替→停止してGUIで唐揚げの味付けを変更→再開→確認中の訂正→送信→管理画面で受付と会計、とする。
韓国料理の別シーンでは、三人で二人前セット・辛さ・取り分けを相談し、重なったチヂミとマッコリの指定を言い直す。訂正後の4,740円を改めて確認・承認し、卓上調理の判断はスタッフへつなぐ。全8会話シナリオ・52客発話の[台本](demo/dialogue.md)と[音声素材](demo/audio.md)を用意する。
MCPの別シーンではメニュー資料→日英下書き→差分確認→公開→GUIと読上げ名への反映を見せる。
録画用の模擬会話ログと実際の音声認識結果を混同しない。性能・精度の実測値に合成ログを使わない。

## 安全なリセット

`demo:reset` と `db:seed` は自worktreeのlocal資源に限定し、remote/productionを拒否する。
R2の対象prefix、D1保存先、DO状態、デモ時計、scenario進行が同じworktreeであることを確認する。
明示リセット時はownerのメールをGoogleの共通名簿へ戻し、パスワードは保持する。旧メールで作成した開発環境もリセット後は同じGoogle名簿で開始できる。通常の再seedではパスワード・手動のメール・所属を保持し、既知の旧デモメールだけを名.姓@店舗名.comへ移行する。
初期化・録画用の特権操作は公開管理者APIの恒久的なbypassとして残さない。

## 店側の会話注文デモ

店舗のowner/adminはsidebar下部の会話注文デモを新しいタブで開ける。端末認可と卓割当ては不要で、同じ管理者が作ったデモだけを操作できる。新規起動は独立し、`demoId`付きURLの再読込では操作状態を復元する。

上部ツールバーで公開中／未公開下書き一式、再読込、プラン、人数、自発接客、リセットを操作する。既定は公開版・プランなし・1人・音声停止。自発接客は選択した設定を引き継ぐ。設定は取り込んだ版を保持し、編集元の変更を自動反映しない。表示中は5秒間隔で設定元の版を確認し、更新がある場合だけ再読み込みボタンを強調して有効にする。通信失敗・取り込み中・更新なしでは無効にする。ツールバーはアイコンと常時表示の操作ラベル・設定名・値を1列に配置し、狭い画面では横スクロールする。

設定変更は音声を停止し、未送信の注文確認を失効する。会話・注文済みスナップショットを保持し、カートを再評価する。無効な商品・選択肢は修正が必要な状態で残す。プラン料金は現在の人数で計算し、プラン変更時だけ開始時刻を更新する。設定に存在しなくなったプランは解除する。リセットは確認後に会話・カート・注文・呼出しを消し、設定・人数・表示モードを保つ。

客向けKioskとHTTP操作ハンドラ、価格・注文確認・音声の業務処理は通常端末と共有する。`table_sessions.kind='demo'`のみ卓IDをnullにでき、`demo_sessions`が作成者・設定元・設定版・設定一式を保持する。元の公開設定と下書きを変更せず、通常の卓・端末を追加しない。営業一覧・履歴・イベントと通知先を分離し、通常APIからのデモ参照・変更も拒否する。

表示は通常iPadが既定で、iPad Air 11インチ・13インチ・ブラウザ領域全体へ切り替えられる。通常iPadとAir 11インチは1180×820／820×1180、Air 13インチは1366×1024／1024×1366 CSS pxを使う。筐体・ベゼル・カメラ・側面ボタンは独自のSVGで軽く再現し、Apple配布画像は同梱しない。iframeのviewportを固定し、枠だけを縮小する。表示切替でiframeや音声を作り直さない。iframeは自アプリのデモURLだけを使い、認証Cookieとマイクに必要な同一originのscript実行を許可する。SafariのブラウザーUI・実機の画素密度やマイク性能の再現は含まない。

デモの注文・会計要求・店員呼出しはデモ内にのみ記録される。実音声の開始は通常と同じprovider接続を使うため、音声の利用設定と資格情報が必要になる。店舗の実営業画面からデモへの提供・支払登録は行わない。
