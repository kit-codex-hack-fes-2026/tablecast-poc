# 製品と業務の仕様

[索引](README.md)

## 目的・範囲

卓上iPadで、声による接客とタッチ式注文を同じカートへ接続する。主対象は居酒屋、食べ飲み放題店、カフェ、訪日客の多い飲食・和菓子店。
来店客は商品説明、文化的背景、カスタマイズ、プランの質問と注文を行う。店舗は全卓の状態、ログ、注文、会計をリアルタイムに確認する。
店舗設定とコンテンツ翻訳は店舗のChatGPT＋MCPに任せる。アプリ内の独自OCR・翻訳Agentは作らない。

必須は日本語・英語。ゲーム、Custom Voice、別モデルへの自動切替、実決済、POS本接続、電話、ドライブスルー、個別会計、本人識別、長期顧客記憶は作らない。

## セッションと権限

Better Authの組織機能で管理者・スタッフを管理し、OAuthとメールアドレスによるログインを提供する。初期のローカル試験はメール・パスワードで完結させ、OAuthは外部接続の統合試験とする。
端末は管理者が承認して店舗・卓へ割り当てる。既存のdevice authorization等の機能を優先する。iPadにスタッフの管理者セッションやモデルAPIキーを置かない。

業務の `tableSessionId` と音声の `voiceSessionId` を分ける。音声停止・再接続・言語切替でカートや注文を消さない。
卓セッション終了時は客向け会話表示と音声文脈を消す。過去客のログは認可された店舗画面だけで参照できる。
店側表示言語は各スタッフの設定、客側表示言語は卓セッションの設定とし、互いに変更しない。

| 主体        | 許可の範囲                                       |
| ----------- | ------------------------------------------------ |
| 客端末      | 自卓のメニュー、カート、注文確認、スタッフ呼出し |
| スタッフ    | 許可店舗の卓・注文・提供・会計確認               |
| 管理者      | 店舗設定、スタッフ・端末管理、設定公開           |
| Voice Agent | 認証された卓セッションの接客操作のみ             |
| 店舗ChatGPT | OAuthで委譲された店舗・操作のみ                  |

## 商品・カスタマイズ

商品ID、価格、販売状態、税・プラン規則は言語非依存。表示名、説明、読み上げ名、検索aliasはja/enで保持する。
表示名と読み上げ名を分離し、原語の固有名が日本語発話へ混ざらないよう店舗設定で読みを登録できる。

カスタマイズは単一選択、複数選択、数量、必須、最小・最大数、価格差、売切、選択肢間の条件を扱う。
辛さ、サイズ、ミルク等の名称をコードの分岐に使わない。商品・選択肢IDと構造化設定で検証する。
必須項目が不足したときはカート行下書きを作り、音声質問と同じ選択UIを表示する。回答ごとに商品を二重追加しない。

条件は現在必要な選択肢依存と組合せ禁止に限定する。汎用ルール言語、eval、店舗提供のJavaScript・SQL実行は作らない。
アレルゲン・ヴィーガン対応は登録された根拠を説明する。含有不明や交差接触不明を安全と断定しない。ミルク変更だけでアレルゲン除去を保証しない。

## 店舗プラン

商品・カテゴリ・タグの対象、利用時間、ラストオーダー、注文上限、累計上限、注文間隔、対象外カスタマイズ、追加料金をデータで管理する。
自由文のプラン説明を価格計算や可否判定として実行しない。人数はスタッフ確認または卓の確定設定を使い、話者ラベル数から決めない。
適用した設定の版を保持し、後日のメニュー公開で過去注文や既に確定したプラン条件を変えない。

## 共通の注文操作

GUI、MastraのTool、必要な管理操作はAPI内の同じ関数を呼ぶ。API内で自分のHTTP endpointを呼び直さない。
カートの変更は版番号付き。商品価格、在庫、プランの判定結果をLLMやブラウザーから採用しない。

確認時に、商品・カスタマイズ・数量・適用プラン・金額を含む変更不可のスナップショットを作る。
画面用表示と読み上げ文は同じスナップショットから生成し、確認本文をLLMへ自由生成させない。
音声では読み上げ完了後の明示承認、GUIでは表示中の版に対する確認ボタンで送信する。音声停止中でもGUI確認は利用可能。
カート変更、訂正、音声の確認途中停止、期限切れ、価格・販売条件の変更で以前の確認を無効にする。

注文送信には冪等性キーを使う。同じ送信を再試行しても一件だけ作る。応答喪失時は送信状態を照会する。
D1のバッチを使う場合、条件付きUPDATEが0行でもSQLエラーにならない点を考慮する。後続の明細・会計・イベント更新を同じ成立条件で守り、競合を実D1相当環境で試験する。[S12](sources.md#s12)

音声の承認判定に完全性はない。DBで保証する前提条件と、実音声テストで観測した誤認識率を区別する。

## 注文・会計・状態

注文は送信済み、受付済み、提供済み、拒否・取消を扱う。会計は確定済み明細、調整、支払記録から計算する。
未送信カートは請求額に含めず別表示する。支払済みの登録はスタッフによるモック操作で、決済処理ではない。
barge-inやAgent停止で、既に送信した注文を取り消さない。取消や支払修正は権限付きの別操作にする。

## リアルタイムとログ

D1に業務状態と確定イベントを同時に保存し、DOが購読者へ通知する。`table_events`を復旧用の永続記録として再利用し、通知のためだけの別イベント基盤を増やさない。
管理画面はスナップショット＋永続カーソルで購読し、接続の合間に発生したイベントも取り直す。重複排除し、通知の到着順やDOの記憶だけを正本にしない。

確定発話、応答の完了・中断、カート変更、注文・会計、スタッフ呼出し、設定公開を記録する。暫定文字列、音声チャンク、内部推論は店舗ログに保存しない。
話者番号は一時的ラベル。本人名・席・会計の根拠にしない。生音声の既定保存と年齢・性別の推定は行わない。

HTTP・Mastra・LiveKit・DBの診断にはtraceId、tableSessionId、turnId、orderId、releaseShaを対応付ける。標準loggerとJSON出力を利用し、独自の観測フレームワークを作らない。
