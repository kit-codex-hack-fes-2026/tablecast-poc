# 製品と業務の仕様

[索引](README.md)

## 目的・範囲

卓上iPadで、声による接客とタッチ式注文を同じカートへ接続する。主対象は居酒屋、食べ飲み放題店、カフェ、訪日客の多い飲食・和菓子店。
来店客は商品説明、文化的背景、カスタマイズ、プランの質問と注文を行う。店舗は全卓の状態、ログ、注文、会計をリアルタイムに確認する。
店舗設定とコンテンツ翻訳は店舗のChatGPT＋MCPに任せる。アプリ内の独自OCR・翻訳Agentは作らない。

必須は日本語・英語。卓上ゲームは[ゲームプラグイン](game-plugins.md)として店舗の承認した版を隔離実行する。Custom Voice、別モデルへの自動切替、電話、ドライブスルー、個別会計、声や顔による本人識別は作らない。会員の明示同意による店舗別の長期記憶・同行履歴・特典は[会員仕様](membership.md)を正本とする。

店舗のTableCast利用契約は組織ごとに管理する。無料プランでメニュー・画面からの注文・店舗管理を利用でき、スタンダードでAI音声接客を利用する。スタンダードは月額基本料とAIの従量料金をStripeで請求する。組織作成時にAIキーを準備し、音声開始時に契約とキーの準備を検査する。利用量は店舗・卓・来店へ紐付け、OpenAI報告費用は運営の組織別収支に使う。詳細は[課金・請求](billing.md)を参照する。

## セッションと権限

Better Authの組織機能で管理者・スタッフを管理し、OAuthとメールアドレスによるログインを提供する。メール認証はマジックリンクとし、Google OAuth・One Tap・パスキーを提供する。全ユーザーは通常利用前にパスキーを登録する。ローカル試験はMailpitとGoogle emulatorを使う。
端末は管理者が承認して店舗・卓へ割り当てる。既存のdevice authorization等の機能を優先する。iPadにスタッフの管理者セッションやモデルAPIキーを置かない。

業務の `tableSessionId` と音声の `voiceSessionId` を分ける。音声停止・再接続・言語切替でカートや注文を消さない。
卓セッション終了時は客向け会話表示と音声文脈を消す。過去客のログは認可された店舗画面だけで参照できる。
店側表示言語は各スタッフの設定、客側表示言語は卓セッションの設定とし、互いに変更しない。

| 主体        | 許可の範囲                                       |
| ----------- | ------------------------------------------------ |
| 客端末      | 自卓のメニュー、カート、注文確認、スタッフ呼出し |
| スタッフ    | 許可店舗の卓・注文・提供・会計確認               |
| 管理者      | 店舗設定、スタッフ・端末管理、設定公開           |
| Voice Agent | 認証された卓セッションの接客操作のみ             |
| 店舗ChatGPT | OAuthで委譲された店舗・操作のみ                  |

## 商品・カスタマイズ

商品ID、価格、販売状態、税・プラン規則は言語非依存。表示名、説明、読み上げ名、検索aliasはja/enで保持する。
表示名と読み上げ名を分離し、原語の固有名が日本語発話へ混ざらないよう店舗設定で読みを登録できる。

メニュー検索は客向け検索画面・音声と店側の商品・カテゴリ・プラン一覧で同じ処理を使う。日英の名前・読み・別名・説明文と、商品の所属カテゴリを対象にする。NFKC・英字大小文字・ひらがな/カタカナ・空白を正規化し、誤字・脱字を許容する。IDは完全一致だけを使い、商品ID・名前・読み・別名への検索語全体の完全一致があればその商品へ絞る。カテゴリ名・読み・別名の完全一致ではそのカテゴリへ絞る。複数語は空白区切りのOR検索で全語一致を上位にし、同順位は登録順、空検索は全件、該当なしは0件とする。1〜2文字は通常の部分一致に限る。漢字の読みは登録済みの読み・別名を使い、意味検索は行わない。

カスタマイズは単一選択、複数選択、数量、必須、最小・最大数、価格差、売切、選択肢間の条件を扱う。

選択肢の条件は同じ商品の選択集合に対するAND・OR・NOTの式で定義する。所有する選択肢が選ばれた場合だけ適用し、参照先の条件へ再帰しない。requiresが成立しなければ未完成カートに保持し、確認・注文を拒否する。excludesが成立すれば組合せを拒否し、カートを変更しない。式の葉は数量1以上の選択の有無であり、数量0は入力として拒否する。自己参照・他商品・参照切れは公開不可、相互参照は許可する。商品・グループの数量制約、売切、価格、プランの判定は引き続き独立して適用する。
辛さ、サイズ、ミルク等の名称をコードの分岐に使わない。商品・選択肢IDと構造化設定で検証する。
必須項目が不足したときはカート行下書きを作り、音声質問と同じ選択UIを表示する。回答ごとに商品を二重追加しない。

条件は現在必要な選択肢依存と組合せ禁止に限定する。汎用ルール言語、eval、店舗提供のJavaScript・SQL実行は作らない。
アレルゲン・ヴィーガン対応は登録された根拠を説明する。含有不明や交差接触不明を安全と断定しない。ミルク変更だけでアレルゲン除去を保証しない。

## 店舗プラン

商品・カテゴリ・タグの対象、利用時間、ラストオーダー、注文上限、累計上限、注文間隔、対象外カスタマイズ、追加料金をデータで管理する。
自由文のプラン説明を価格計算や可否判定として実行しない。人数はスタッフ確認または卓の確定設定を使い、話者ラベル数から決めない。
適用した設定の版を保持し、後日のメニュー公開で過去注文や既に確定したプラン条件を変えない。

## 共通の注文操作

GUI、Agents APIのfunction、必要な管理操作はAPI内の同じ関数を呼ぶ。API内で自分のHTTP endpointを呼び直さない。
カートの変更は版番号付き。商品価格、在庫、プランの判定結果をLLMやブラウザーから採用しない。

確認時に、商品・カスタマイズ・数量・適用プラン・金額を含む変更不可のスナップショットを作る。
画面用表示と読み上げ文は同じスナップショットから生成し、確認本文をLLMへ自由生成させない。
音声では読み上げ完了後の明示承認、GUIでは表示中の版に対する確認ボタンで送信する。音声停止中でもGUI確認は利用可能。
カート変更、訂正、音声の確認途中停止、期限切れ、価格・販売条件の変更で以前の確認を無効にする。

注文送信には冪等性キーを使う。同じ送信を再試行しても一件だけ作る。応答喪失時は送信状態を照会する。
D1のバッチを使う場合、条件付きUPDATEが0行でもSQLエラーにならない点を考慮する。後続の明細・会計・イベント更新を同じ成立条件で守り、競合を実D1相当環境で試験する。[S12](sources.md#s12)

音声の承認判定に完全性はない。DBで保証する前提条件と、実音声テストで観測した誤認識率を区別する。

## 注文・会計・状態

注文は送信済み、受付済み、提供済み、拒否・取消を扱う。会計は確定済み明細、調整、支払記録から計算する。
未送信カートは請求額に含めず別表示する。スタッフによる手動の支払登録と、Squareから照合した支払記録を区別する。手動登録は入金の記録操作であり、外部の決済要求を送らない。
barge-inやAgent停止で、既に送信した注文を取り消さない。取消や支払修正は権限付きの別操作にする。

### Squareとの会計連携

POS連携はSquareの本番接続を標準とする。管理者がOAuthで接続し、Square店舗を選び、TableCast商品を一つのSquare商品バリエーションへ、オプションをSquareカスタマイズへ対応付ける。管理画面とagent pluginのMCPから同じ業務操作を使う。既存の商品名・価格・翻訳・画像は自動同期しない。接続状態、再認証、解除は既存の店舗管理画面、会計は既存の卓詳細から扱う。商品一覧・注文画面を別に作らず、既存部品を使う。客端末・音声・MCPから決済を開始しない。

商品対応は商品を親、そのカスタマイズを子にした階層型のOOUIとし、小さい画像・名称・価格・Square対応先・状態を表示する。商品単位でページを分け、子だけが検索・絞込みに一致したときも親商品を残す。画像の有無で名称の位置を変えず、Squareの登録名は言語を仮定せず原文を保つ。全体件数と対応済み・未対応・重複・要確認を検索・絞込みにかかわらず集計する。重複先の名称と価格差・削除・利用不可を表示し、商品とカスタマイズの対応漏れを確認できる。別商品で同じSquareカスタマイズを使う正常な再利用は重複扱いにしない。共有するTableCastカスタマイズは一つの入力と保存値を複数商品へ反映する。重複警告によって既存の保存契約を変更せず、入力を勝手に削除しない。カスタマイズの画像・名称・説明・個数・追加料金は注文選択・注文済み明細・商品設定・POSで共通の表示部品を使う。

agent pluginは連携状態、TableCast商品とカスタマイズ、Square店舗・端末・商品バリエーションと親ごとのカスタマイズ候補を取得し、対応付け全件を版付きで保存できる。管理者権限とread/write scope、店舗境界、会計中の固定、競合制御はGUIと共通にする。原文名・価格・親子関係で照合し、既存対応を保持して確実な対応をまとめて保存する。曖昧な候補は推測で確定しない。初回のSquare OAuth同意は接続画面から行う。

スタッフは来店全体の会計をプレビューし、開始・照会・取消を操作する。未送信カートが空で、注文の受付・提供判断が済んだことを開始条件にする。通常商品、有料オプション、プラン人数料金、プラン内商品の0円、APIで確定したクーポン、正負の調整を集約し、調整へ計上した割引を二重加算しない。商品対応付けの欠落・削除・店舗での利用不可・登録価格差・未対応構造を理由付きで示す。税対応はJPYの税込10%とし、Square catalogの税設定が対応範囲外なら開始を拒否する。プランによる0円化と登録価格差は区別し、Squareの計算合計が請求額と1円でも違えばTerminal APIへ要求しない。0円会計は端末を使わずSquareの0円注文で精算する。

開始前に明細・金額・対応付けの版と冪等キーを永続化し、一来店で進行できる会計を一つにする。処理中は注文追加・取消、人数・プラン・割引・調整と手動支払登録を止める。変更はSquare側の取消完了後に行い、結果不明の間は固定を解放せず再決済しない。同じ内容の再送は同じキーを使い、応答喪失・再読込みから照会で回復する。

署名付きWebhookは重複を排除し、接続先のSquare APIから店舗・注文・金額・決済状態を照合して支払記録へ一度だけ反映する。Webhookの到着だけで支払済みとしない。処理中・支払済み・取消・要確認を日英で示し、接続環境や検証手順を通常の製品UIへ説明文として持ち込まない。支払完了で提供済みや閉卓を自動確定しない。Square以外のprovider、部分払い・返金・在庫同期は対象外とする。

## リアルタイムとログ

D1に業務状態と確定イベントを同時に保存し、DOが購読者へ通知する。`table_events`を復旧用の永続記録として再利用し、通知のためだけの別イベント基盤を増やさない。
管理画面はスナップショット＋永続カーソルで購読し、接続の合間に発生したイベントも取り直す。重複排除し、通知の到着順やDOの記憶だけを正本にしない。

確定発話、応答の完了・中断、カート変更、注文・会計、スタッフ呼出し、設定公開を記録する。暫定文字列、音声チャンク、内部推論は店舗ログに保存しない。
話者番号は一時的ラベル。本人名・席・会計の根拠にしない。生音声の既定保存と年齢・性別の推定は行わない。

HTTP・GPT-Live・Agents API・DBの診断にはtraceId、tableSessionId、turnId、orderId、releaseShaを対応付ける。標準loggerとJSON出力を利用し、独自の観測フレームワークを作らない。

## 用件案内と人への引き継ぎ

店員呼び出し前に用件を確認する。既に分かっていれば聞き直さず、店舗の登録案内や関連商品で対応できればその方法を案内する。用件不明時の確認は一度とし、人を明確に希望する客を案内で引き止めない。直接呼び出しは常時利用でき、要約モデルの応答を待たない。

店舗案内は任意の`guides`として日英の名称・読み・説明・別名、関連商品ID、案内リンクを公開設定に保存し、メニューと同じ下書き・検証・公開・履歴・MCP編集を使う。関連商品の価格・売切・必須選択・注文確定は既存の業務APIを正本とする。

人への依頼は`staff_calls`に一件ずつ保存し、日本語の要約、今回の依頼の原文・言語、案内済み内容、未解決点、呼出日時、対応済み日時を持つ。再送・連打で重複依頼を作らず、呼出中・対応済みの状態を店員と同じ来店の客へ共有する。対応済み後も履歴を残す。個人的な会話履歴・会員の過去の相談は引き継がず、今回の用件だけを共有する。既存ログから未記録のメモや対応状態を推測して補完しない。

用件相談の商品自動候補は、登録された名称・読み・別名の完全一致に限定する。説明文の水という語や部分一致だけで酒類等を候補に混ぜない。名称が異なる商品は店舗案内の関連商品として明示する。
