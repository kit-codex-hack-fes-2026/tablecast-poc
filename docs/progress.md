## 基盤の決定

- Bun 1.3.13、Node 24.7以上、TypeScript 6.0.3。Cloudflare公式 `@cloudflare/vitest-plugin` 1.1.4とVitest 4.1.11を使用。
- 通常開発はCloudflare Vite Pluginの補助WorkerでAPIを起動し、Service BindingでWebと接続する。
- 開発資源と秘密情報はworktreeの `.local` に分離する。既存 `.env.local` を自動読込みして有料サービスへ接続しない。
- Web、API、Pythonを分担し、ルートlockfileとmigrationは統合担当が管理する。
- ユーザーの追加指定で、shadcn・Base UI・Tailwind・Lucide・Simple Flagsのデザインシステムを導入。装飾用の見出しや補助文を削除。
- デモは日本酒28種を含む各60商品・3店舗・2組織・36卓。商品画像は生成原本を保存し、R2からImages bindingで640px WebPとして配信する。
- 音声の外部前提がすべて揃った時だけローカルAPIの音声を有効化する。初期カタログのVoice IDは未設定。

## 統合時に修正した問題

ルートの `bun run storybook` で起動しHTTP200を確認した。専用portを使い、自動繰上げを禁止する。一時的な未await Promiseを `no-floating-promises` が検出して終了1となることも確認し、その一時ファイルは削除した。

JSONCの末尾カンマを通常JSONで読んでいた起動不良を、導入済みの標準 `jsonc-parser` に置換した。本番相当実行はCloudflare Vite previewで、公式buildが生成したmanifestから2 Workersへ接続する。ローカル資源名と秘密を含むbuildは共有cacheへ入れない。

Mastraの管理adapter経由のNode初期化を除き、公式 `RequestContext` と `Agent.stream` をHonoから使う。公式 `Mastra({ logger: false })` でprovider例外の会話本文を一般ログへ出さず、HTTPエラーと失敗turnは維持する。Viteが生成した2 Workersを実workerdで起動し、GUI・OAuthを通した。

WebSocketの受信予約コード1005/1006/1015を再送していた不具合を、固定1000の終了応答へ修正した。handlerを削除する案は採用版の実試験で正常終了しなかったため、必要な明示返信を残した。Wranglerの接続台帳も公式 `WRANGLER_REGISTRY_PATH` でworktree内へ分離した。`dev:parity` は実行ごとに最新のbuildを確認して再起動する。

E2Eで卓を開いた後に画面を再読込みする際、選択店舗が初期値へ戻ることを見落としていた。試験内で対象店舗を再選択し、Chromium/WebKit両方の4件が成功した。

通常の全体チェックはサンドボックスによるuv cacheへの書込み拒否があったため、同じ無課金コマンドを必要権限で再実行した。テストをskipや型キャストで通していない。

MCPは認証済み管理者によるクライアント事前登録を使う。匿名DCRの有効化は自動承認レビューで拒否されたため変更していない。この制約下で組織選択・同意・PKCEまでブラウザー試験に合格した。

Wrangler 4.129.0の複数config起動では、リクエスト切断でProxyControllerが `Network connection lost` を致命的エラーとして終了した。予約WebSocketコードの修正後にも再現する別問題であり、[対応する未反映の上流修正](https://github.com/cloudflare/workers-sdk/pull/15207)を確認した。独自patchや自動再起動で隠さず、導入済みの公式Vite previewへ切り替えた。独立したpreview環境では、正常WebSocket終了10回とタブ閉鎖10回の後も毎回health 200、プロセスと認証の維持を確認した。統合した `dev:parity` でもChromium/WebKitの注文・認証4件が20.4秒で成功した。

最終の起動経路でも正常終了10回・タブ閉鎖10回後のhealth 200と認証維持を確認した。previewの秘密ファイルは0600、client成果物への秘密値の一致は0件だった。通常buildへ戻した際は、配備用のWorker名とmanifestへ戻り、ローカル `.dev.vars` が残らないことを確認した。結果を `.local/tablecast-preview-final.json`、T01の日本語画面を `.local/tablecast-kiosk.png` に残した。

## 継続監査での修正

料金プランの対象外商品にもラストオーダー時刻で確認期限を切っていたため、締切後の通常料金の料理を注文できなかった。対象プラン行を含む時だけ期限を制限するよう修正し、対象外の確認・注文成功と対象内の拒否を実D1で確認した。

使用中の卓への開卓要求がUNIQUE制約エラーで500になっていた。空席の時だけセッションを挿入し、その成功時だけ開卓eventを作成する。既存卓と同時開卓の後着要求は409になり、先行セッションとカートを維持する。event保存の途中失敗ではセッションも残らないことを実D1で確認した。

同じ設定公開要求が並行すると、後着のCASが0件でも恒久的な公開キーの条件で履歴を再挿入し、UNIQUE制約エラーになった。SQLite標準の `changes()=1` でこのbatchの更新だけを連鎖し、同じ要求の再送には保存済み結果を返す。確認失効は対象が0件以上なので、1件ずつの更新連鎖の最後に実行する。同キーの別下書き、異なるキーの同じ版、途中失敗の全体rollbackも検証した。

店舗全体の設定公開eventが客の卓event取得から除外され、客画面に古いメニューが残っていた。同店舗の公開通知だけを管理metadataなしで渡し、取得した設定版を客のcatalog query keyへ含める。設定版が変わったら古い商品ダイアログを閉じる。他店舗・他卓・別種の店舗eventを除外する実D1試験も追加した。

設定公開のブラウザー試験はあかり店の空席T10で行う。WebSocket通知を遮断し、正規の下書き作成・価格変更・検証・公開から、HTTP event取得と客画面の価格切替まで通す。終了時は自分の公開版から変わっていないことを確認して元の設定を新規公開し、試験卓を閉じる。公開・復元の版と監査履歴は通常の記録として残る。既存のT12は使用中だったため変更しない。

管理画面の文字を200%へ拡大すると固定幅のサイドバーからラベルがはみ出した。最小幅を維持しながら内容幅で広がるよう修正した。日英・Chromium/WebKitで文字収まりと画面を確認し、キーボードによるログイン・言語切替・ダイアログfocus・画面移動とreduced motionも検証した。実iPadやブラウザー全体zoomの証明とは区別する。

別のHTTPクライアントによるカート変更を、WebSocket切断中の5秒pollと実サーバーへの再接続後の通知から回収した。古い確認を閉じて商品行を重複表示しないことと、ブラウザー時計だけを進めた確認期限の失効をChromium/WebKitで確認した。注文試験もスタッフ日英と単一・複数・数量型の選択へ拡張し、画面の選択内容と実DBのカート・注文snapshotの一致を確認した。

管理ログはAPIが保存する `order.status` の状態、`billing.payment`、`billing.adjustment`、`configuration.published`、`confirmation.prepared` を使うよう修正した。以前は別名のイベントを表示側で仮定し、受付・提供・会計などが汎用更新表示になっていた。実API形式の部品試験を日英で追加し、Storybook22件が成功した。管理画面自身のWebSocketを切断する日英・Chromium/WebKitの4件でも、HTTPからの会計event回収、再接続後の通知、履歴件数と残高の一致を確認した。

MCPの公開確認URLが存在しない `/admin` を指していたため、実在する `/admin/live` へ修正した。公式MCP ClientとStreamableHTTP transport、実OAuth code・PKCE・同意を通す試験3件で、日英商品・speechName・価格・プラン・キャストの更新、検証失敗と修正、差分、承認値だけでは公開できないことを確認した。読取専用scope、OAuth対象組織、店舗team、下書きの店舗境界、要求時点のrole変更も確認した。外部ChatGPTの接続試験とは区別する。

管理画面に商品単価・販売可否・日英表示名/読上げ名/説明の手動編集を追加した。保存は既存PUTとdraft版を使い、未保存中は検証・公開できない。保存結果をquery cacheへ反映し、閉じて再表示しても旧版へ戻らないことを確認した。確認リンクの店舗・下書きはログインを挟んでも保持し、店変更や遅い応答で別の下書きを開かない。日英・両ブラウザーの4件で編集・保存・再確認・検証・明示公開を通し、確認画像8点を目視した。

設定編集をカテゴリ・商品・選択肢・プランの追加/削除、安全情報・画像参照・alias・依存/排他条件・キャスト指示まで拡充した。下書きの作成・破棄もGUIから既存APIへ接続する。未保存の追加を取り消した場合は保存済み対象へ戻し、作成応答待ちに別下書きを編集させない。新しい日英・Chromium/WebKitの4件で保存後の再表示、無効なラストオーダーの検証理由、修正と再検証、破棄、公開catalog不変を確認した。画像28点の表示範囲を分担して目視し、横切れ・固定footerとの重なりがないことを確認した。WebKit画像外の一部下部項目は操作・保存・再表示をE2Eで、表示をChromium画像で確認した。

検証結果はAPI所有の9種類のcode/path/paramsへ変更し、Webで対象名と理由を日英表示する。旧DBの文字列エラーは保存設定から再評価し、読み取りでは版・検証状態・DBを変えない。商品・グループ・選択肢の追加/削除に含まれる価格や安全情報も重要な差分として扱い、構造化内容を省略せず表示する。旧形式互換・公開拒否・全検証コード・追加削除の差分を含めAPI67件、表示部品26件が成功した。
