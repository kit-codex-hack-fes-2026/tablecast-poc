# BDDとケース設計

## 一つの規則を決める

Givenは必要な状態、Whenは結果を生む一つのきっかけ、Thenは利用者・公開API・永続化先に現れる結果とする。一つのシナリオは原則一つのtrigger・guard・atomic outcomeを扱う。

例えば「保存失敗時にprimary row、quota、auditのすべてがrollbackされる」は同じ原子的結果なので、複数assertionで一緒に確認する。別々に変更できる検索・作成・削除を一つの長いjourneyへまとめない。

自然言語は業務用語、意味のある合成データ、意図、必要な前提、一つの規則に集中させる。説明は通常5行程度で読めるようにするが、コード行数の上限にはしない。初期表示等で前提が不要ならGivenを省略し、空のコメントを作らない。

## MECEを設計に使う

全入力の直積ではなく、**明示した契約範囲で、同じ振る舞いになる入力を分け、境界と相互作用を確認する。** MECEやcoverageだけで未知の不具合まで安全と断言しない。

1. 入力領域・状態・役割・資源所有者・外部失敗を洗い出す。
2. 結果が変わる条件をdecision tableへ並べる。各行のguardを排他的にし、到達可能な領域を覆う。
3. 同じ結果・同じ失敗原因の行は同値クラスとして代表値を選ぶ。
4. 大小や期間の境界は直前・境界・直後を選ぶ。未設定、null、空、0を同義と決めつけない。
5. 組合せでのみ生じるリスクを追加する。独立した表示軸は代表組合せ、認可やデータ安全性の相互作用は必要な組合せを明示的に検証する。
6. 各行に所有層と観測結果を割り当て、未検証・非自動化には理由と代替確認を残す。

複数の拒否理由が同時に成立する場合は、どの拒否を優先する契約か確認する。個別guardのテストでは他の条件を有効にし、別のguardで偶然通る偽陽性を避ける。

## リスクに応じた観点

| 観点               | 適用時に確認すること                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| 認証・認可・tenant | 未認証、許可/不許可role、他tenant資源、membership失効、権限変更。拒否後に書込み・漏洩がないこと。 |
| 入力               | 有効、境界、欠落、異常形式、サイズ超過。契約外入力をサーバーで拒否できること。                    |
| 状態遷移           | 許可/不許可遷移、terminal state、再実行、取消後の遅延応答。                                       |
| 永続化             | commit、途中失敗rollback、制約違反、関連行・quota・auditの整合。                                  |
| 競合・再試行       | 同時更新、重複要求、idempotency、再送、順序逆転、部分失敗。                                       |
| HTTP・外部         | timeout、network failure、上流4xx/5xx、error変換、Cookie、Origin、stream切断。                    |
| UI                 | loading、empty、error、success、pending、retry、keyboard、focus、主要responsive境界。             |
| 時刻・並び順       | 有効期限の境界、timezone/DST、同順位、paginationの重複・欠落。                                    |

全機能に全行を追加しない。その機能が所有するリスクだけを選び、重要な欠落には根拠を求める。property-based testは多数の入力に共通する不変条件がある場合、既存ツールで検討する。

## 例: tenant内のIssue更新

契約例: 認証済み編集者が自tenantのIssueを更新できる。不許可の更新は永続化せず、更新と監査は一緒にcommitする。

| 規則・リスク     | 代表ケース                       | 最低十分な所有層                      | 上位固有の確認                        |
| ---------------- | -------------------------------- | ------------------------------------- | ------------------------------------- |
| 編集権限の判断   | memberとviewerの許可差           | 権限判断の単体（Vitest）              | HTTP入口がpolicyを適用する代表拒否    |
| tenant分離       | 編集者が他tenantのIDを指定       | DB・API統合（Vitest + 実DB）          | 認証contextからtenantが渡る接続       |
| 入力上限         | 上限直前・上限・超過             | schema・domain単体（Vitest）          | HTTPへ不正入力が届いた場合のerror変換 |
| 原子性           | audit保存の失敗で更新もrollback  | transaction統合（Vitest + 実DB）      | 同じ失敗をE2Eで再演しない             |
| 失敗時の操作継続 | 保存失敗後も入力を保持してretry  | feature統合（Storybook/Vitest + MSW） | 実routeのError Boundaryとは区別       |
| 最終接続         | 許可された更新がreload後も見える | フルスタックE2E（Playwright）         | 実API・DB・認証を接続していること     |

期待値は仕様の具体値から書く。SUTと同じ計算・条件分岐で期待値を生成すると、同じ誤りを両側に複製する。
