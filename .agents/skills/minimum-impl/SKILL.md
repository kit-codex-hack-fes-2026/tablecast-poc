# 最小実装

GPT 5.6 Sol, 6 Astraはオーバーエンジニアリングしがち。
要求・受入条件・安全性・互換性・必要な検証を保ち、所有して理解・保守・試験する独自実装を減らす。行数ではなく、分岐・状態・変換・抽象化・依存・設定・重複した知識・テスト準備・運用の総負担で判断する。コードを短くするためにエラー処理、データ保全、アクセシビリティ、性能、必要なテストを削らない。

## 実装前の確認

必要な範囲を実物で確認してから案を決める。

1. 要求、受入条件、不変条件、非対象と、対象ディレクトリの指示・仕様・ADR・テスト契約を読む。
2. 採用する言語・ランタイム・プラットフォーム・フレームワーク・ライブラリの対象バージョンの公式仕様・docs・examplesを確認する。慣例フォルダ構造、命名、公開entrypoint、設定、呼び出し方を踏襲し、公式にない部分は既存採用例に合わせる。
3. 現在の差分・対象SHA、変更対象、全呼び出し元、データフロー、依存関係、関連テストを確認する。説明だけから実装や差分の存在を仮定しない。
4. monorepoでは対象workspaceのmanifest、exports、依存方向、検証scriptと、再利用するclient・schema・component・query・factoryを読む。名前や責務を推測しない。
5. 認証・認可・tenant変更ではpermissionの正本、membership/role判定、resource query、error契約を確認する。DB更新ではschema、migration、adapter、transaction・audit・rollback経路を確認する。

複数workspaceをまたぐ案は、各所有実装・公開境界・呼び出し元・関連テストを確認してから確定する。未確認なら暫定案、足りない証拠、設計が変わる理由、次に読む箇所を示す。

状態モデル、権限、tenant境界、失敗分類、公開response、互換性、データ保全を左右する未確定事項を勝手に仕様化しない。安全に決められない部分は確認を求め、独立して進められる範囲を扱う。仮定と確定事項、仮定変更で影響する契約・file・testを区別し、仮定を検証済みと報告しない。

## 選択順序

最初に受入条件を満たす手段で止める。

1. 変更不要、設定変更、既存機能の呼び出し、不要コードの削除。
2. 既存の関数・型・component・schema・query・client・factory・公開entrypointの再利用。
3. 言語・型システム・ランタイム・標準ライブラリ・標準ツール。
4. OS・ブラウザ・HTML・CSS・SQL・DB制約などのプラットフォーム機能。
5. フレームワークの標準機能・規約・設定・拡張点。
6. 導入済みライブラリの公式API・設定。
7. 新規依存と小さな独自実装を、保守・試験・供給網・更新・bundle・実行環境の総負担で比較。
8. なお必要な要求固有の独自実装だけを追加。

標準機能と同じ独自処理を重ねない。bug fixは全呼び出し元を確認して根因のある共有経路で直し、既存利用者への影響を検証する。

画面設定や単発操作はComputer Use / Codex Browserや既存CLIで済ませる。反復実行や決定的な変換が必要な場合だけ再利用スクリプトを検討する。

## DRYとYAGNI

- 同じ変更理由を持つ業務規則、schema、validation、対応表、定数、serialization、error mappingは正本を一つにする。既存の共通経路を使い、置換した旧実装は利用実態を確認して削除する。
- 見た目が似ていても意味が違えば統合しない。transport契約、domain model、UI専用validationの違いを確認する。共通化で引数・分岐・間接参照・型・fixture・理解コストが増えるなら局所的な重複を許容する。
- 現在の要求、実在する呼び出し元、実装済みvariantで必要なものだけ作る。将来用のwrapper、provider、plugin、設定、feature flag、互換層、未使用API、共有package、generic Result、base class、registry、DI containerを先回りして追加しない。
- 将来機能が必要になった時点で、共有する意味論・security・失敗契約・契約test・移行手順を決める。

## 分割・factoryを許容する条件

純粋な業務判断とI/O（ネットワーク、DB、filesystem、時刻、乱数、環境変数）、または入力検証・domain処理・serializationは、次を満たすなら分割してよい。

- 中核ロジックを直接、速く、決定的にテストできる。
- I/O側が薄く、domainへframework固有型やproviderの詳細を漏らさない。
- fixture・mock・分岐・総コード量・理解コストのいずれかが実際に減る。
- 横流しだけのservice/repository/use case層を増やさず、DIを実在する副作用境界や差し替え対象に限る。

portは利用するapplication/moduleが所有し、runtime間で形だけ似た境界を汎用契約にまとめない。

factoryは実在する生成種類、識別値による選択、反復するfixtureや複雑な既定値を集約し、可読性と総負担を改善する場合に使う。一種類でもこの効果があればよい。直接生成より不透明なfactoryや、将来の種類のためのregistry・builder・containerの連鎖は作らない。

## フルスタック・モノレポの責務

実際の所有者・公開entrypoint・依存方向を調べ、次の責務を写像する。表の名前に合わせて構造を新設しない。

| 責務                                               | 所有境界と判断                                                                                                    |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 画面、ルーティング、ブラウザ状態、UI入力           | Webと公開API client。表示だけで完結するならAPI/DBを増やさない。DBや別runtimeの内部へdeep importしない。           |
| HTTP契約、認証・認可、tenant、業務判断             | API/serverの既存経路。権限・業務規則の正本を画面側へ複製しない。                                                  |
| schema、制約、migration、query、transaction、audit | DBを所有するserver/data。既存経路で満たせるならテーブルやrepository抽象を追加しない。                             |
| queue、定期処理、Worker、Agent                     | 受入条件・データフローに含まれるruntimeだけを公開境界から変更する。                                               |
| 複数consumerが使う同じ意味のドメイン非依存契約     | 既存共有packageと公開exports。実際に重複を減らせる場合だけ共有し、feature固有UI・認可・DB queryの箱を新設しない。 |

## 実装・検証・報告

1. 根因のある所有境界へ一貫した差分を入れ、無関係な整理や将来用一般化を混ぜない。置換した重複・不要wrapper・互換経路は既存利用者を確認して削除する。
2. 独自の分岐・変換・状態遷移・権限・外部契約・回帰を、最も低い十分なテストレイヤーで担保する。標準機能の内部は再試験せず、固有の設定・境界・統合を検証する。具体的な設計はfullstack-web-testingに従う。
3. 既存scriptと指示で対象のtest/typecheck/lint/formatを確認し、影響する依存workspaceやrootの必須check/buildへ広げる。根拠のない高価なE2E・有料テストは足さない。失敗をテスト削除で隠さない。
4. 採用した標準機能と理由、変更した責務、削除・見送りの理由、安全性・互換性への影響、残る独自実装、実行した検証と結果、未実施・未確定事項を簡潔に報告する。

UIまたはエンドユーザーの振る舞いが変わる場合は、Codex Browser / Playwright / OpenScreenなどで実動作の画像か動画を撮り、成果報告と作成・更新するPRの関連説明中へキャプション付きで必ず埋め込む。撮ったままでよく、装飾編集や独立したメディア見出しは不要。秘密情報の除去や必要な圧縮は行う。

## レビュー・監査

差分レビューでは対象SHAと実在する差分を確認し、標準機能の再実装、同じ知識の重複、未使用の一般化、横流しの層、不要な依存、副作用混在、過剰なfactory、workspace境界違反を呼び出し元・exports・依存・testで裏付ける。上の条件を満たす分割やfactoryは存在だけを問題にしない。

各指摘には優先度、実在するfile:line、証拠、保守負担、単純な代替案、挙動・互換性・testへの影響を含める。証拠不足と確認済み所見を分け、問題がなければそう述べる。この観点だけで正確性・security・performanceの総合レビュー済みとはしない。

リポジトリ監査では指定範囲の候補を利用実態と効果で優先順位付けし、置換案、削減できる独自実装、移行リスク、必要なtest、変更順序、境界を越える場合の所有者と公開entrypointを示す。レビュー・監査だけの依頼では実装を始めない。
