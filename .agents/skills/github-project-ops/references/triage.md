# トリアージ

Issue本文、受け入れ条件、依存、関連PR、現在の目標を読んで分類する。優先度、変更量、難しさ、失敗時の影響を混同しない。根拠のある値を選び、重大な判断変更はIssueコメントに理由を残す。

## Priorityは必須

全管理対象のIssue・epicへ設定する。未判断は未トリアージとして扱い、空欄を任意・最低優先度と解釈しない。通常の作業と判断できれば `p1-normal` を使い、重要度が不明なら根拠を調べる。

従来の尺度を維持し、**0が最低、3が最高**とする。既存Projectが逆の尺度を採用している場合は、意味を対応付けて利用し、番号だけで順位を判断・上書きしない。

| 値          | 意味   | 判断の目安                                                                                   |
| ----------- | ------ | -------------------------------------------------------------------------------------------- |
| p0-optional | 任意   | 当面実施しなくても利用者・開発・安定性にほぼ影響せず、後続も止めない。                       |
| p1-normal   | 通常   | 機能完成や品質に価値があり、順序は柔軟に変えられる。通常作業の基本。                         |
| p2-high     | 高     | 現在の目標やリリースに直接必要、または重要な後続作業を止めている。                           |
| p3-critical | 最重要 | 重大障害、データ破壊・漏洩、既定ブランチ破損、リリース停止など、直ちに対応すべき影響がある。 |

小さい変更でも重大障害なら高優先度になる。大きい変更だから高優先度とは限らない。すべてを最重要にせず、影響・緊急性・依存の根拠を確認する。

## Size・Complexity・Risk

末端Issueをトリアージするときは次の観点を評価する。既存の同じ意味の分類があればそれを使う。

| 観点       | 段階                                           | 判断すること                                                                                                        |
| ---------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Size       | s0-tiny / s1-small / s2-medium / s3-large      | 差分量とレビュー量。極小、局所的、複数箇所だが一度に確認可能、一度では把握しにくい大きさ。                          |
| Complexity | c0-none / c1-simple / c2-moderate / c3-complex | 判断の未知性。ほぼ判断不要、既存設計で解ける、複数案や互換性の検討が必要、契約・設計自体の不確実性が高い。          |
| Risk       | r0-none / r1-safe / r2-moderate / r3-dangerous | 失敗時の影響。影響がほぼない、局所的で戻せる、利用者やAPI・DB等へ影響、データ破壊・漏洩・不可逆な移行等の重大影響。 |

ファイル数・行数だけでSizeを確定しない。`s3-large` は独立して確認できる成果への分割を検討し、`c3-complex` は先に明らかにする問いや調査を示す。数値だけで作業を自動停止したり、Issueを分割・起票したりしない。

`r3-dangerous` ではレビュー責任者、影響範囲、検証と復旧方法を明らかにする。必要な判断やレビューをPriorityの高さで省略しない。

## 工数と確度

Effortは実装、直接確認、テスト、文書、通常のレビュー修正を含む作業量として概算する。CI・レビュー・外部判断の待ち時間と分け、単位はProject内で揃える。Sizeの段階を工数として合計しない。

確度を記録するなら、未知要素が多い `ec0-low`、境界は明確だが一部不明な `ec1-medium`、類似実績と確認方法が揃う `ec2-high` を目安にする。

工数と確度は未定でもよい。親epicと子Issueで二重計上せず、集計する場合は末端Issueを使う。厳密な見積りを通常の着手条件にしない。

## 再トリアージ

受け入れ条件、依存、利用者への影響、リスク、現在の重点、期限が変わったらPriorityと関係する分類を見直す。中止された依存Issueを、成果が完成したものとして扱わない。

Issue分割・契約・担当変更が必要なら `github-issue-pr-ops` の運用に従う。予定の調整だけでAssigneeを外したり、branchやPRを作り直したりしない。
