# PR本文とマージ

## タイトル

PRタイトルは利用者の言語で、変更内容が分かる自然な言葉にする。Conventional Commitsのtype・scopeやGitmojiの接頭辞を付けない。例えば「期限切れセッションのエラー表示を統一する」とする。作成・更新時には本文だけでなくタイトルも確認する。

## 本文

対象リポジトリのPRテンプレートを確認して優先する。なければ[同梱テンプレート](../assets/.github/pull_request_template.md)を使う。CLIからも同じ項目を埋め、非UIの変更で省略しない。小さな変更は各項目を短く書き、文書などで自動テストが適用外なら理由と代わりの確認を示す。

実際の問題と変更後の振る舞いを先に説明する。比較が判断に影響した標準機能・代替案と採用理由、残る独自実装の必要性、テスト層ごとの保証と選定理由を書く。必要な選択はminimum-implとfullstack-web-testing、具体的なrunnerは対象リポジトリのテスト方針とpackage scriptsを参照する。

本文は最終差分と確認済みheadに合わせる。Issueの契約が変わった場合はその理由を含めて更新し、単なる試行の履歴や削除済みテストを最終成果として残さない。実装Issueを閉じる行は原則一つとし、参照Issueやepicを閉じない。

## プレビューのリンク

アプリやコンポーネントカタログのpreviewが利用できる場合は、確認対象のURLをPR本文へ記載する。

- 配備jobや通知から、対象PRと最新head SHAに対応する実URLを取得する。命名規則から推測したURLを配備済みとして載せない。
- 変更した画面・コンポーネントへの直リンクは実ページや生成manifestで確認する。
- 確認した配備SHA・状態と必要なアクセス手順を書く。未配備・失敗・未確認の場合はその状態と理由を残す。push後は新しいheadへの配備を確認して更新する。
- 通常のMarkdownリンクを使い、認証tokenや署名付きURLを貼らない。UI変更では画像・動画と併記し、リンクだけで実動作の証拠を代替しない。

## 確認と証拠

画像・動画の添付が必要なのは、UIの見た目や操作を変更する場合だけとする。CLI・API・設定・文書の検証は、実行コマンドと結果をテキストやコードブロックで示す。ログを画像化するためにブラウザー等へ表示する手順は不要である。

UIの証拠には次を適用する。

- Codex Browser / Playwrightで実際の変更後の画面を撮影する。操作の流れやデスクトップアプリはOpenScreenやComputer Useの撮影機能を使う。
- PRへ添付するスクリーンショットは、ブラウザーで実際のWeb・API・ローカルseed DBを接続した画面を撮る。Storybook、Vitest Browserの単独部品、test-support fixtureをPRの実画面証拠へ代用しない。Storybookは状態・動作・アクセシビリティの検証へ使い、プレビューURLを併記する。店舗ロゴ・商品・選択肢・資料の画像decode完了と、手動編集・保存・再読込を確認し、captionへ対象SHA・操作・viewportとseed DB接続を記載する。
- 変更点が判別できる状態を選ぶ。比較が必要なら変更前も撮影する。撮ったままでよく、見栄えのための編集は不要。
- アニメーションや音声停止など時間変化が成果なら動画または適切な動的メディアを使い、静止画だけで動作を示したことにしない。音声の確認には音声を含む記録を使う。
- 関連する説明の直後へ埋め込み、直下に操作・確認結果の短いキャプションを添える。画像・動画専用の見出しは作らない。指定がなければPR本文を使い、コメントへの添付でもその説明中に埋め込む。
- 投稿前に秘密情報が写っていないこと、文字が読めること、動画が再生できることを確認する。必要に応じて元ファイルを残して圧縮する。
- [添付手順](attachments.md)に従って標準CLIの`--attach`でアップロードし、投稿後に表示・再生を確認する。
- 撮影・添付できない場合は未完了として原因を報告し、添付済みやレビュー準備完了と扱わない。

実行したテストや操作と結果を記載し、必要な確認を未実施なら理由を書く。内部処理だけの変更には、適切なテスト結果を示す。

## レビュー対応

人によるレビューも自動レビューも、指摘を対象commit・実装・利用版と照合する。有効な指摘は修正と関連する検証を行い、誤検知なら根拠を示して解消する。P0・P1等の重大な指摘は未解決のままマージせず、優先度ラベルや自動レビューであることだけで採否を決めない。

レビュー対応が依頼範囲にある場合、修正をpushしたら対象SHAと変更・確認結果をレビュースレッドへ返信し、対応済みのスレッドを解決する。push・rebase後はレビュー対象SHAと現在のheadを区別する。再レビューの依頼は利用先の仕組みとユーザーの許可に従い、特定のサービスの設定や起動コメントを一律に要求しない。指摘なしやレビュー完了をCI成功・承認・マージ許可の代わりにしない。

## Draft・レビュー・マージ

新規PRはDraftで作り、実装・本文・必要な検証と添付を揃える。Draft解除やマージはユーザーが許可した範囲で行う。

マージ直前に最新head SHA、必須チェック、レビュー、競合、リポジトリの保護・マージ方式を確認する。保護の迂回はしない。待機中やキューへの投入をマージ成功として報告しない。

通常PRでは `gh pr checks` / `gh pr view` / `gh pr merge` を使い、必要に応じて `--match-head-commit` で確認済みheadへ限定する。Stackは[stacked PR](stacked-prs.md)に従う。

マージ後にPRと対応Issueの状態を確認し、[Issueの完了判定](lifecycle-comments.md#完了判定)を行う。pushやrebaseでheadが変わった場合は、そのSHAに対する確認結果を取得し直す。

マージキュー対応のCIを整備する場合だけ、[CI例](../assets/.github/workflows/merge-queue-checks.example.yml)の `merge_group` を既存ワークフローへ統合する。
