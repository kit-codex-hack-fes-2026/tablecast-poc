# PR本文とマージ

## 本文

[リポジトリのPRテンプレート](../../../../.github/pull_request_template.md)を本文の正本として使う。CLIからも同じ項目を埋め、非UIの変更で省略しない。小さな変更は各項目を短く書き、文書などで自動テストが適用外なら理由と代わりの確認を示す。

実際の問題と変更後の振る舞いを先に説明する。比較が判断に影響した標準機能・代替案と採用理由、残る独自実装の必要性、テスト層ごとの保証と選定理由を書く。必要な選択はminimum-implとfullstack-web-testing、TableCastのrunnerは[テスト戦略](../../../../docs/testing.md#変更に応じた検証)を参照する。

本文は最終差分と確認済みheadに合わせる。Issueの契約が変わった場合はその理由を含めて更新し、単なる試行の履歴や削除済みテストを最終成果として残さない。実装Issueを閉じる行は原則一つとし、参照Issueやepicを閉じない。

## 確認と証拠

**UIまたはエンドユーザーへの振る舞いが変更されるときは、画像か動画を必ずPR本文またはPRコメントへ添付する。** CLIなど画面以外の利用経路でも、実行と結果が分かる画像・動画を用意する。説明文やテストログだけで代用しない。

- Codex Browser / Playwrightで実際の変更後の画面を撮影する。操作の流れやデスクトップアプリはOpenScreenやComputer Useの撮影機能を使う。
- 変更点が判別できる状態を選ぶ。比較が必要なら変更前も撮影する。撮ったままでよく、見栄えのための編集は不要。
- アニメーションや音声停止など時間変化が成果なら動画またはAnimated WebP/APNGを使い、静止画だけで動作を示したことにしない。
- 関連する説明の直後へ埋め込み、直下に操作・確認結果の短いキャプションを添える。画像・動画専用の見出しは作らない。指定がなければPR本文を使い、コメントへの添付でもその説明中に埋め込む。
- 投稿前に秘密情報が写っていないこと、文字が読めること、動画が再生できることを確認する。必要に応じて元ファイルを残して圧縮する。
- [添付手順](attachments.md) に従ってGitHub画面からアップロードし、投稿後に表示・再生を確認する。
- 撮影・添付できない場合は未完了として原因を報告し、添付済みやレビュー準備完了と扱わない。

実行したテストや操作と結果を記載し、必要な確認を未実施なら理由を書く。内部処理だけの変更には、適切なテスト結果を示す。

## Draft・レビュー・マージ

新規PRはDraftで作り、実装・本文・必要な検証と添付を揃える。Draft解除やマージはユーザーが許可した範囲で行う。

マージ直前に最新head SHA、必須チェック、レビュー、競合、リポジトリの保護・マージ方式を確認する。保護の迂回はしない。待機中やキューへの投入をマージ成功として報告しない。

通常PRでは `gh pr checks` / `gh pr view` / `gh pr merge` を使い、必要に応じて `--match-head-commit` で確認済みheadへ限定する。Stackは [stacked PR](stacked-prs.md) に従う。

マージ後にPRと対応Issueの状態を確認し、[Issueの完了判定](lifecycle-comments.md#完了判定) を行う。pushやrebaseでheadが変わった場合は、そのSHAに対する確認結果を取得し直す。

マージキュー対応のCIを整備する場合だけ、[CI例](../assets/.github/workflows/merge-queue-checks.example.yml) の `merge_group` を既存ワークフローへ統合する。
