# PR本文とマージ

## 本文

[リポジトリのPRテンプレート](../../../../.github/pull_request_template.md)を本文の正本として使う。CLIからも同じ項目を埋め、非UIの変更で省略しない。小さな変更は各項目を短く書き、文書などで自動テストが適用外なら理由と代わりの確認を示す。

実際の問題と変更後の振る舞いを先に説明する。比較が判断に影響した標準機能・代替案と採用理由、残る独自実装の必要性、テスト層ごとの保証と選定理由を書く。必要な選択はminimum-implとfullstack-web-testing、TableCastのrunnerは[テスト戦略](../../../../docs/testing.md#変更に応じた検証)を参照する。

本文は最終差分と確認済みheadに合わせる。Issueの契約が変わった場合はその理由を含めて更新し、単なる試行の履歴や削除済みテストを最終成果として残さない。実装Issueを閉じる行は原則一つとし、参照Issueやepicを閉じない。

## コンポーネントプレビューのリンク

PR本文の変更内容またはテスト戦略と確認結果へ、配備済みのStorybookとReact Emailのpreview URLを記載する。自動通知コメントだけで済ませず、両カタログが配備されるPRでは変更対象外のものも含めて入口を載せる。

- [カタログ配備](../../../../docs/deployment.md#prのstorybookメールカタログ)の通知コメント・配備job・release情報から、対象PRと最新head SHAに対応する実URLを取得する。命名規則から推測したURLを配備済みとして載せない。
- 変更したコンポーネントがある場合は、Storybookの該当Story、React Emailの該当テンプレートと言語へ直接移動するリンクも付ける。実ページまたは生成manifestでパスを確認する。カタログを変更していなければ、その旨を添えて入口へリンクする。
- Cloudflare Accessへのログインが必要なこと、確認した配備SHAと状態を明記する。未配備・失敗・未確認の場合はその状態と理由を残し、成功URLとして扱わない。push後は新しいheadへの配備を確認して更新する。
- URLは通常のMarkdownリンクで記載し、認証tokenや署名付きURLを本文へ貼らない。リンクは実画面の画像・動画と併記し、それぞれの検証対象を説明する。

## 確認と証拠

画像・動画の添付が必要なのは、UI・Webアプリの見た目や操作を変更する場合だけとする。CLI・API・設定・文書の検証は、実行コマンドと結果をテキストやコードブロックで示す。ログを画像化するためにブラウザー等へ表示する手順は不要である。

UI・Webアプリの証拠には次を適用する。

- Codex Browser / Playwrightで実際の変更後の画面を撮影する。操作の流れやデスクトップアプリはOpenScreenやComputer Useの撮影機能を使う。
- 変更点が判別できる状態を選ぶ。比較が必要なら変更前も撮影する。撮ったままでよく、見栄えのための編集は不要。
- アニメーションや音声停止など時間変化が成果なら動画またはAnimated WebP/APNGを使い、静止画だけで動作を示したことにしない。
- 関連する説明の直後へ埋め込み、直下に操作・確認結果の短いキャプションを添える。画像・動画専用の見出しは作らない。指定がなければPR本文を使い、コメントへの添付でもその説明中に埋め込む。
- 投稿前に秘密情報が写っていないこと、文字が読めること、動画が再生できることを確認する。必要に応じて元ファイルを残して圧縮する。
- [添付手順](attachments.md) に従ってGitHub画面からアップロードし、投稿後に表示・再生を確認する。
- 撮影・添付できない場合は未完了として原因を報告し、添付済みやレビュー準備完了と扱わない。

実行したテストや操作と結果を記載し、必要な確認を未実施なら理由を書く。内部処理だけの変更には、適切なテスト結果を示す。

## レビュー対応

Codex CloudのPRレビューも対応対象とする。ユーザーごとの有効化と`@codex review`による手動呼出しは[セットアップ](../../../../docs/setup.md#codex-cloudのprレビュー)を参照する。

指摘を対象commit・実装・利用版と照合する。P0・P1はマージ前に必ず対応し、未解決のままマージしない。有効な指摘は修正と関連する検証を行い、誤検知なら根拠を示して解消する。優先度ラベルや自動レビューであることだけで、指摘を採用・無視しない。

修正をpushしたら、対象SHAと変更・確認結果をレビュースレッドへ返信し、対応済みのスレッドを解決する。push・rebase後はレビュー対象SHAと現在のheadを区別し、追加レビューが必要ならPRへ`@codex review`を投稿する。指摘なしやレビュー完了をCI成功・承認・マージ許可の代わりにしない。

## Draft・レビュー・マージ

新規PRはDraftで作り、実装・本文・必要な検証と添付を揃える。Draft解除やマージはユーザーが許可した範囲で行う。

マージ直前に最新head SHA、必須チェック、レビュー、競合、リポジトリの保護・マージ方式を確認する。保護の迂回はしない。待機中やキューへの投入をマージ成功として報告しない。

通常PRでは `gh pr checks` / `gh pr view` / `gh pr merge` を使い、必要に応じて `--match-head-commit` で確認済みheadへ限定する。Stackは [stacked PR](stacked-prs.md) に従う。

マージ後にPRと対応Issueの状態を確認し、[AGENTS.mdの完了の確認](../../../../AGENTS.md#完了の確認)に従って対応worktreeの開発用プロセス・コンテナの停止と残存確認を行ってから、[Issueの完了判定](lifecycle-comments.md#完了判定)を行う。pushやrebaseでheadが変わった場合は、そのSHAに対する確認結果を取得し直す。

マージキュー対応のCIを整備する場合だけ、[CI例](../assets/.github/workflows/merge-queue-checks.example.yml) の `merge_group` を既存ワークフローへ統合する。
