# Issue本文とForms

Issueには「何を、なぜ変えるか」「完了をどう判断するか」を書く。変更ファイルや参照資料は分かる範囲で添える。全Issueに同じ見出しやファイルglobを強制しない。

- 機能・作業: 背景、成果、受け入れ条件、確認方法。
- 不具合: 期待動作、実際の動作、再現手順、影響、修正の確認方法。
- 調査: 答える問い、判断に必要な証拠、成果物。時間枠は必要な場合だけ設ける。
- epic: 目的、成果の境界、子Issueを含む完了条件。

採用方針と意思決定の理由、minimum-implに照らした既存・標準機能の再利用と必要な独自実装、fullstack-web-testingに照らしたレイヤー（具体的なランナー）と保証の分担を書く。Issueでは計画として示し、未決定なら必要な証拠を明記する。文書・調査・epicでは成果に合う粒度にし、適用外の理由と代わりの確認を書く。実施結果はPRへ反映する。

画像・動画は関連説明中へ埋め込み、直下に操作・確認結果の短いキャプションを添える。専用見出しや装飾編集は不要で、撮ったままを使う。

非スコープは誤解されやすい隣接機能がある場合だけ書く。作業体制をIssueの成果に含めない。API・DB・画面にまたがっても、一つの利用可能な成果として確認できるなら機械的に分割しない。

親子関係、依存、Assignee、MilestoneはGitHub標準メタデータで設定する。判断の背景として関連Issueを本文から参照してよい。参照資料の版が判断に影響する場合はコミットSHAへ固定する。

```markdown
## 目的

検索結果から、一致した場面へ移動できるようにする。

## 受け入れ条件

- [ ] 検索結果を選ぶと対象の場面から再生される。
- [ ] 一致する場面がないときは理由が表示される。

## 意思決定と最小実装

既存の検索結果とプレイヤーの移動APIをつなぐ。移動先の計算を複製せず、要求固有の接続だけを追加する。

## テスト戦略と確認方法

移動先の計算規則は既存の単体テスト（Vitest）を利用し、検索結果からの操作と移動APIの接続を統合テスト（Storybook / Vitest）で確認する。E2E（Playwright）は検索から再生までの代表経路に絞る。
対象あり・対象なしの検索結果で操作し、移動先と表示を確認する。
変更後の実動作を画像または動画に撮影し、PRの関連説明中へキャプション付きで埋め込む。
```

起票・更新時に主目的のラベルを付ける。例:

```bash
gh issue create --repo OWNER/REPO --title "検索結果から一致した場面へ移動する" --label feat --body-file issue.md
gh issue edit ISSUE_NUMBER --repo OWNER/REPO --add-label fix --body-file issue.md
```

[Issue Forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms) を導入する場合は、`assets/.github/ISSUE_TEMPLATE/` から必要なフォームをコピーして既存の入力項目へ合わせる。フォームの `labels` に指定するラベルはリポジトリに作成しておく。
