# Issueのライフサイクルとコメント

Issueの流入整理、トリアージ、着手、作業中の判断、レビュー、停止・再開、引き継ぎ、中断、完了・中止を扱う。Projectsの有無にかかわらず適用する。

## 記録の置き場所

- Issue本文: 現在の目的、受け入れ条件、確認方法。前提が変わったら更新する。
- GitHubメタデータ: Assignee、ラベル、親子関係、依存、Milestone。担当と排他制御はAssigneeだけで判断する。
- PR本文・レビュースレッド: 実装差分、検証、画像・動画、レビュー指摘への対応。
- Issueコメント: 判断の履歴、理由、証拠、阻害要因、引き継ぎ、次に進める条件。

コメントから現在の担当を決めない。branchやPRは継続する作業を把握するために参照し、追加のロックにはしない。Stackの現在の順序・baseはGitHubメタデータで確認する。

## コメントを残すタイミング

意味のある判断や状態変化を残す。経過時間だけの報告、通常のCI実行・レビュー待ち、構成を変えないrebaseのたびにコメントを増やさない。PRやメタデータから分かる事実はリンクで参照し、同じ一覧を転記し続けない。

| 段階                 | 行うこと・コメントに残す内容                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 流入整理・トリアージ | 流入元、期待する成果や影響、判断根拠、未確定事項、次の確認。Issue本文・ラベル・関係へ現在の判断を反映する。                                                |
| 着手条件の確認       | 受け入れ条件と確認方法、未解決の依存や外部阻害要因、Assigneeを確認する。重要な判断や停止直後の再開では根拠を残す。通常の着手はメタデータ更新だけでもよい。 |
| 作業中・再トリアージ | 設計判断、前提変更、証拠、契約への影響、次の操作。契約が変わったらIssue本文も更新する。                                                                    |
| レビュー             | 実装と確認結果はPRへ集約する。IssueにはPRから分からない外部判断や注意点だけ残す。修正要求は実装へ戻して対応し、外部阻害要因と混同しない。                  |
| 阻害要因による停止   | 理由、依存先、試したこと、解除できる人または条件、再確認条件。通常のレビュー・CI・マージ待ちは停止扱いにしない。                                           |
| 阻害要因の解消・再開 | 解消の証拠、再確認した前提、次の操作。最新のAssigneeとIssue本文・関係を確認して再開する。                                                                  |
| 担当の引き継ぎ       | 引き継ぐ理由、担当変更の決定、既存branch・PR、完了済みと未完了、検証状況、未push差分の保存先、再開手順。                                                   |
| 中断・担当解放       | 理由、保存した成果、残作業、再開条件を記録する。一時中断と担当解放を区別する。                                                                             |
| 完了                 | 成果物、受け入れ条件の確認結果、後続作業。PRで十分説明できる場合は重複コメントを省略してよい。調査やPRなしの作業はIssueへ完了根拠を残す。                  |
| 中止                 | 実行しない理由、根拠、代替や関連Issueを記録し、未完了として閉じる。依存するIssueへの影響も確認する。                                                       |
| 再オープン           | 完了・中止を取り消す理由と新しい証拠、以前の成果への影響を残し、受け入れ条件・関係・担当を再確認する。                                                     |

## 担当変更と作業の保全

別のAssigneeがいる場合、明示された引き継ぎがなければ着手せず担当を確認する。コメントの先着順や無応答の長さを根拠に担当を差し替えない。

引き継ぎが決まったら、作業成果と未push差分を保全して再開情報を残し、Assigneeを更新・再取得する。既存branchやPRを引き継いでよく、存在することだけを競合理由にしない。

一時中断では担当を維持してよい。担当を解放する場合は再開に必要な情報を残してAssigneeを外し、反映を確認する。コメントだけで担当解除済みと扱わない。中断や引き継ぎを理由にbranch・PR・未push差分を自動削除しない。

Projectsを併用する場合は、確認した進捗に合わせてStatus等を更新する。Projectの値からIssueの担当を決めない。

## コメント例

該当する項目だけ使い、空欄や「なし」の列挙を残さない。絵文字や見出しは読みやすさのためであり、機械的な状態マーカーではない。証拠はIssue・PR・CI・仕様など後から確認できるリンクで示し、秘密情報や非公開の作業URLを含めない。

### 判断・前提変更

```markdown
🔄 前提変更を受けて再トリアージした。

- きっかけと証拠: ...
- 判断と理由: ...
- 受け入れ条件・関係への反映: ...
- 未確定事項と次の確認: ...
```

### 停止

```markdown
⛔ 外部の阻害要因のため停止する。

- 理由: ...
- 依存先と証拠: ...
- 試したこと・保存した成果: ...
- 解除できる人または条件: ...
- 再確認条件: 上流PRのマージなど、再開判断に必要な変化を書く。
```

### 再開

```markdown
🔓 阻害要因が解消したため再開する。

- 解消内容と証拠: ...
- 再確認した前提・受け入れ条件: ...
- 次の操作: ...
```

### 引き継ぎ・中断

```markdown
🤝 作業を引き継ぐ。

- 理由と担当変更の決定: ...
- 引き継ぐbranch・PR: ...
- 完了済み・未完了: ...
- 検証結果と未実施の確認: ...
- 未push差分の保存先と扱い: ...
- 次の操作・再開条件: ...
```

中断時は冒頭を中断理由に変え、担当を維持するか解放するかを書く。

### Stack構成変更

PRの追加・除外・順序変更・分割・統合では、判断の履歴を残す。通常の同期では不要。

```markdown
🧱 Stackの構成を変更した。

- 理由: ...
- 変更前後のPR・base: ...
- 影響するIssue: ...
- 再確認したhead・レビュー・CIと、残る確認: ...
```

この記録は変更時点の履歴であり、現在の構成はGitHubから確認する。

### 完了・中止・再オープン

```markdown
✅ 完了条件を確認した。

- 成果物またはマージ: ...
- 受け入れ確認: ...
- 未実施の確認と影響: ...
- 後続Issue: ...
```

中止では「実行しない理由・根拠・代替」を、再オープンでは「再開理由・新しい証拠・再確認する条件」を記録する。

## 完了判定

- 実装Issue: 対応PRがマージされ、受け入れ条件と必要な検証を満たしている。自動クローズされたことだけで完了と判断しない。
- 調査・PRなしの作業: 成果物、採否判断、証拠、後続作業の要否をIssueに残して閉じる。
- epic: 必須の子Issueが完了し、成果全体の条件を満たしている。中止された子を自動的に完了へ数えない。
- Stack: マージ対象の範囲と各Issueを個別に判定し、残る上段やepicを一括完了にしない。
